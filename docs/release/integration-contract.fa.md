# DARK XRAY PRO — قرارداد یکپارچه‌سازی حسابداری با محصول

وضعیت: **طرح اجرایی مبتنی بر سورس؛ نه پیاده‌سازی تازه، نصب یا مجوز مهاجرت.**
تاریخ بررسی: ۱۶ اکتبر ۲۰۲۶. این سند شرط تحویل را مشخص می‌کند؛ هیچ گیت اجرایی صرفاً با وجود سند، سبز نمی‌شود.

## ۱. مبنای بررسی و اختلاف‌هایی که باید رفع شوند

مبنای PRO در این بررسی Commit `077ed6d0608cdccb07ffdacaaedc3de24475ee15`، درخت `fafaadb07241f43451c34acce83466fd0ea616e0` و schema اصلی نسخهٔ ۷ است. این مرجع در همین نوبت از GitHub خوانده شد؛ «نسخهٔ نصب‌شده» یا آخرین نسخهٔ احتمالی در آینده محسوب نمی‌شود.

کیت ورودی `DARK_XRAY_PRO_integrated_acceptance_kit.zip` با SHA-256 برابر `c7bdecc502c537873aa9713a11cb3c0744ad9a5892646e221caa29c9798d3dde` از فایل همین گفتگو خوانده شد. این کیت جایگزین `main` نیست. پوشه‌های کاری حسابداریِ منتشرنشدهٔ سرور نیز نسخه‌های متفاوت‌اند و بدون مقایسه نباید روی کیت یا `main` کپی شوند.

**اختلاف نسخهٔ هسته:** CI این Commit از Xray `v26.9.9` با هش آرشیو `1eb9175d0f0a8f8149c9230a7fc5ae66ce332ed20a53155ce61fe62e3f58b7df` استفاده می‌کند؛ runner کیت برای `v25.9.11` و هش `e3e26d15b0306401a6ec80e46bf165669c0fc2ac32626f19ad35071bd721115c` قفل شده است. نتیجهٔ یکی، نتیجهٔ دیگری نیست. نسخهٔ پایهٔ محصول از CI همان Commit گرفته می‌شود؛ نسخهٔ قدیمی فقط آزمون سازگاری جداگانه است. هیچ انتخابی در این سند ادعای «جدیدترین نسخه» نیست.

**اختلاف دامنهٔ آزمون:** تابع `newCoreLedgerDatabase` در `integration/realcore/ledger_database_project_test.go` واقعاً از `business.Open` و `CreateClient` استفاده می‌کند؛ اما احراز هویت گزارش در آزمون ترکیبی هنوز callback آزمایشی است، نه حلقهٔ کامل Node Registry و Agent. عبور از آن آزمون، پایان یکپارچه‌سازی محصول نیست.

## ۲. مرز تحویل بعدی

مالک یا نمایندهٔ مجاز در UI یک مشتری تازهٔ PRO می‌سازد؛ همان UUID به اینباند مجاز متصل می‌شود؛ Agent تازهٔ جفت‌شده تنظیمات را دریافت می‌کند؛ ترافیک واقعی دو مشتری عبور می‌کند؛ مصرف هر مشتری در پنل دیده می‌شود؛ با پایان سهم A، تمام اتصال‌های A قطع و **همان اتصال قبلی B** سالم می‌ماند. تمدید A پس از ثبت تراکنش و مجوز تازه امکان اتصال جدید می‌دهد، بدون صفرشدن مصرف گذشته. هیچ مشتری تولیدی برای این آزمون منتقل نمی‌شود.

## ۴. قواعد غیرقابل‌حذف حسابداری

**واحد و محل شمارش.** دادهٔ پروتکلی، payload در Gateway و بایت کارت شبکه سه چیز متفاوت‌اند. هر epoch باید `meter_model`، نسخهٔ آن و واحد را داشته باشد. به‌صورت پیش‌فرض تغییر معیار شمارش در وسط اشتراک ممنوع است؛ نگاشت معیار قدیمی به جدید باید ثبت و تطبیق داده شود. این سند قیمت‌گذاری تازه یا برابری خودکار معیارها تعیین نمی‌کند. حجم ذخیره‌شده بایت صحیح است؛ نمایش «گیگ» قرارداد مستقل دارد و تبدیل ضمنی GB/GiB مجاز نیست.

**مصرف یکتا.** کلید دوره حداقل نود + installation + boot + هویت فرآیند/زمان شروع + config hash + binding hash است. شناسهٔ گزارش و hash محتوا تکرار را تشخیص می‌دهند. همان گزارش، همان رسید و صفر اثر تازه دارد؛ همان شناسه با محتوای متفاوت conflict است. تراکنش شامل delta، cursor، receipt، eligibility و invalidation است؛ رسید پیش از commit صادر نمی‌شود.

**سهم چند نود.** برای هر مشتری حجمی: `committed_usage + مجموع سهم معتبرِ هنوز حساب‌نشده <= purchased_limit`. سهم، سقف تجمعی یک epoch است، نه عددی برای جمع‌زدن روی هر پاسخ. انقضای زمانی مجوز به‌تنهایی سهم گزارش‌نشده را آزاد نمی‌کند. تخصیص تازه نیازمند تسویهٔ تأییدشده یا تطبیق صریح است؛ در غیر این صورت توقف امن و کم‌فروشی بهتر از مصرف پنهان است.

**نامحدود با بی‌حساب متفاوت است.** اعتبار فروش نامحدود بر مبنای کاربر×ماه حفظ می‌شود. ثبت مصرف و محدودیت تعداد کاربر/IP همچنان قرارداد مستقل دارند. برای حجمی IP نامحدود یک انتخاب مجاز است، نه حذف کلی کنترل IP. پذیرش HWID یا IP واقعی پشت تانل نیازمند شواهد مسیر است.

**تاریخ و لغو.** زمان خرید، زمان اولین اتصال و انقضای مطلق جدا هستند. مجوز از انقضای واقعی مشتری فراتر نمی‌رود. تمدید، اتمام حجم را پس از ثبت می‌تواند برطرف کند ولی disable دستی یا archive را نه. حذف مشتری، گروه یا اینباند اجازهٔ پاک‌کردن مصرف یا refund خودکار ندارد.

**تفاوت دو مجوز.** مجوز فرآیند `managedxray.Lease` در PRO با مجوز حجم `usagepolicy.Grant` کیت یکی نیست. حق عبور باید اشتراک هر دو مجوز، وضعیت مشتری و پوشش واقعی حسابگر باشد. heartbeat، ACK فرآیند یا handshake TCP جای هیچ‌کدام نیست. قرارداد کلیدها، نسخه، ترتیب و expiry باید domain-separated بماند.

## ۵. چرخهٔ اجرا و بازیابی

۱. پیش از بازکردن Listener، هویت نصب و تنظیمات ثابت، نگاشت کاربران، محل شمارش و مجوز معتبر بررسی شوند؛ baseline کامل در صف پایدار نوشته شود. هیچ پنجرهٔ «ابتدا ترافیک، بعداً حسابگر» پذیرفته نیست.

۲. با مسیر پوشش‌داده‌شده، هر کاربر از سهم مشترک همهٔ اتصال‌های خودش استفاده کند. اطلاعات کاربر پس از احراز هویت استخراج شود، نه از IP مشترک یا فیلد قابل‌ادعای مشتری.

۳. نمونه/نوشتن واقعی به checkpoint و سپس صف پایدار می‌رسد. تنها رسید دقیقِ قدیمی‌ترین گزارش صف آن را آزاد می‌کند. گزارش قبلی و تصمیم قبلی نمی‌توانند مهلت را تمدید کنند.

۴. تغییر محدودکننده، دسترسی لغوشده را فوراً از منبع authority خارج کند. شکست Apply نباید با Rollback آن دسترسی را برگرداند؛ اسنپ‌شات مالی و خرج‌شده هرگز همراه تنظیمات Xray rollback نمی‌شود.

۵. خاموشی سالم ابتدا پذیرش و نوشتن تازه را متوقف می‌کند، جریان‌های متعلق به همان دوره را می‌بندد، نتیجهٔ نوشتن درحال‌انجام را مشخص و گزارش نهایی را پایدار می‌کند. رهاکردن reservation فقط پس از receipt نهایی معتبر است. «درخواست توقف» با «توقف تأییدشده» فرق دارد.

۶. در crash، `unknown_tail`/hold ثبت می‌شود؛ دورهٔ قبلی صفر، سالم یا نهایی فرض نمی‌شود. recovery مجوز تازه و اتصال تازه می‌خواهد. قطع فرآیند آزمایشی اثبات قطعی برق یا reboot ماشین نیست؛ هرکدام گیت مستقل دارند.

## ۶. ترتیب تغییرات محصول

**I1 — تثبیت مبنا:** source SHA، فایل‌های وابستگی، مدل schema، اختلاف همهٔ packageهای منتشرنشده و هر باینری ثبت شوند. وجود تعارض، توقف patch و بررسی دستی؛ نه force overwrite.

**I2 — Store و API:** صفر فقط برای مشتری جدید؛ import baseline مستقل؛ تراکنش‌ها و رسید؛ endpointهای احرازشده و دادهٔ خواندنی UI. فعال‌بودن schema باید sticky باشد تا حذف flag محدودیت حجم را دور نزند. در این مرحله runtimeِ دارای ادعای metered باید تا آماده‌شدن I3 مسدود بماند.

**I3 — Agent و هسته:** supervision واقعی، کلیدها، epoch، queue/recovery، پوشش مسیر و توقف فقط کاربر. این مرحله با فرایندهای واقعی HUB و Agent و Registry تست می‌شود، نه تماس مستقیم تست با متدهای Store.

**I4 — پذیرش و نمایش:** UI مصرف واقعی، اتمام سهم، تمدید، حفظ اتصال B، تست pin و transportهای موردنیاز، ثبت هزینهٔ منابع. آزمون مستقل و شمارهٔ تست زیاد جای این مرحله نیست.

**I5 — نصب آزمایشی روی سرور جدید:** نصب نسخهٔ یکپارچه با حساب و نود تازه، فقط پس از I1 تا I4؛ هیچ اطلاعات تولیدی منتقل نمی‌شود. سپس Subscription، Dark Swap واقعی، ربات‌ها و جریان فروش تکمیل می‌شوند.

**I6 — مهاجرت:** فقط پس از تکمیل برابری امکانات، پایداری، rehearsal و تأیید صریح مالک. قرارداد جداگانهٔ همین پوشه تعیین‌کننده است.

## منابع کدی خوانده‌شده

مرجع همهٔ مسیرهای PRO، SHA ابتدای سند است. `.github/workflows/ci.yml` محل pin هسته؛ `cmd/node-agent/main.go` حلقهٔ واقعی Agent؛ `internal/business/store.go` schema و خرید؛ `internal/business/inbounds.go` انتخاب UUID و انقضا. مسیرهای `usage*` و `integration/realcore` به کیت با هش مشخص ابتدای سند اشاره می‌کنند، نه به فایل‌های فرضیِ `main`.
