# DARK XRAY PRO — قرارداد مهاجرت کامل، حفظ سرویس و امکان بازگشت

**این سند هیچ Import، انتقال Bot، تغییر DNS، پورت یا فرمانی روی سیستم قدیمی اجرا نمی‌کند.** مهاجرت پس از تکمیل نسخهٔ کامل و تأیید مالک است؛ نمایش UI و CI سبز به‌تنهایی اجازهٔ انتقال نیستند.

مبنای PRO: `077ed6d0608cdccb07ffdacaaedc3de24475ee15`.
مبنای سورس قدیمی خوانده‌شده: `ed66ded4ec09c9d023635f64d9b05eb592ce06a1`.
دیتابیس تولیدی، توکن واقعی یا backup مشتریان در این بررسی خوانده نشده‌اند. تطبیق جدول‌ها با فایل صادرشدهٔ واقعی هنوز لازم است.

## ۱. یافته‌ای که مسیر Import را تغییر می‌دهد

در `backend/backup.py`، تابع `prepare_telegram_disaster_recovery` توکن ربات‌ها را خالی، enabled را صفر و update_offset را بازنشانی می‌کند؛ state فروش را نگه می‌دارد و forum را نیازمند rebind می‌کند. این رفتار برای **disaster recovery** نوشته شده؛ نباید بدون تغییر قرارداد به‌جای **planned migration** اجرا شود.

مهاجرت PRO باید شناسهٔ Bot و ارتباط آن با مالک/نماینده/مشتری، سفارش، cursor یا watermark معتبر و روش پردازش به‌دفعات را حفظ کند. secrets در مخزن یا گزارش نمی‌آیند؛ در staging غیرفعال و رمزگذاری‌شده‌اند. فعال‌سازی Bot فقط پس از تحویل انحصاری مصرف update و پذیرش endpoint جدید است. تعویض توکن یا Bot ID بدون تصمیم مستقل، معادل حفظ Bot قبلی نیست.

در همان ماژول، `LIMIT = 256 * 1024 * 1024` تعریف شده است. بنابراین پشتیبانی از backup حدود یک گیگابایت یا بزرگ‌تر نباید از وجود این ماژول نتیجه‌گیری شود؛ آرشیو واقعی با مصرف RAM، صحت و بازیابی باید آزموده شود. بالا بردن ثابت بدون بررسی همهٔ مسیرهای خواندن و رمزگذاری کفایت نمی‌کند.

## ۲. قلمروهایی که باید با هم تطبیق داده شوند

|---|---|---|
| مالک و نمایندگان | هویت منطقی، نقش، فعال/غیرفعال، اختیارها، اعتبار حجمی و کاربر×ماه، audit | یک‌به‌یک‌بودن نگاشت و عدم افزایش دسترسی؛ اعتبار و سابقهٔ debit/grant برابر |

| مشتری Restore | namespace مستقل، public_token، legacy_host/path/query/url، baseline و مصرف جدید، گروه و mappings | با مشتری عادی یا آمار اصلی قاطی نشود؛ promotion قبلی و promotion جدید متمایز و صریح باشند |

فهرست جدول‌های مشاهده‌شده در سورس قدیمی شامل `restore_subscriptions`, `restore_domains`, `restore_events`, `core_inbounds`, `telegram_bots`, `telegram_forums`, `telegram_forum_topics`, `commerce_products`, `commerce_prices`, `commerce_gateways`, `commerce_orders`, `commerce_payments`, `commerce_gateway_events`, `customer_wallets`, `customer_wallet_ledger`, `customer_topups`, `customer_support_tickets`, `customer_support_messages`, `customer_support_quick_replies`, `telegram_customer_settings` است. این فهرست از کد خوانده شده، نه از snapshot تولیدی؛ کامل‌بودن export را تضمین نمی‌کند.

`backend/dark_restore.py` صریحاً legacy URL اجزاشده، `legacy_upload`, `legacy_download`, `legacy_total`, `legacy_expire` و public token را ثبت می‌کند. Import نباید با ساخت دوبارهٔ مشتری و UUID تازه، قرارداد حفظ اشتراک را دور بزند. sentinel نامحدود، انقضای صفر، میلی‌ثانیه/ثانیه و زمان اولین اتصال باید جداگانه تبدیل شوند.

## ۳. قرارداد سند مهاجرت و نگاشت

هر اجرا باید `migration_id`, `source_repository_commit`, `source_export_schema`, `snapshot_id`, زمان checkpoint و hash آرشیو، `target_commit`, schema مقصد، قرارداد واحدها و نتیجهٔ validation داشته باشد. namespace هویت حداقل `(source_panel_id, entity_kind, source_id)` است؛ یک ID یکسان در native و Restore به معنی یک مشتری نیست.

برای هر entity نتیجهٔ `preserved`, `transformed`, `blocked` یا `explicitly_excluded` ثبت شود. `blocked` مانع انتقال است؛ `explicitly_excluded` فقط با تصمیم ثبت‌شدهٔ مالک برای قابلیت واقعاً قابل‌حذف پذیرفته است، نه برای حذف دادهٔ مالی. هیچ ردیفی بی‌گزارش skip نمی‌شود.

شناسه‌ها و مقادیر حساس در گزارش عمومی منتشر نشوند. برای مقایسهٔ خروجی‌ها از fingerprint/HMAC با کلید حسابرسی خصوصی مشترک استفاده شود؛ password hash، Bot token، subscription secret و private key در GitHub، CI، stdout و فایل عمومی نباشند. حفظ قابلیت login با password قدیمی نیازمند adapter هش معتبر است؛ مجبورکردن به reset باید صریح و برنامه‌ریزی‌شده باشد. نشست‌های مرورگر قدیمی و tokenهای Agent تازه‌سازی می‌شوند و «حساب کاربری محفوظ» با «همان session» یکی نیست.

## ۴. ترتیب rehearsal تا cutover

**M0 — فهرست و export:** نسخهٔ واقعاً نصب‌شدهٔ قدیمی و قابلیت‌های فعال خوانده شوند. backup رمزگذاری‌شدهٔ consistent با مجوز مالک گرفته شود؛ سازگاری سورس GitHub به‌جای schema فایل واقعی فرض نشود.

**M1 — بازیابی قرنطینه:** فقط در مقصد خالی و مستقل؛ شبکهٔ خروجی به Bot/payment واقعی غیرفعال. health، UUIDها، روابط و دفتر بررسی شوند. هیچ webhook یا polling تولیدی با واردکردن رکورد فعال نشود.

**M2 — تطبیق کامل:** count و fingerprint هر قلمرو، expiry مطلق، quota/usage، balance و grant/debit، سفارش/پرداخت، روابط Restore و گروه تطبیق داده شوند. Import دوباره نباید duplicate یا debit بسازد. crash وسط import و شروع دوباره نیز سنجیده شود.

**M3 — پذیرش امکانات:** owner و representative واقعیِ آزمایش، همهٔ پروتکل‌های موردنیاز، خرید/تمدید/تیکت/نمایش تاریخ، نود، مسیرهای Direct/Tunnel/Swap، Backup/Restore و رفتار فشار/قطعی/ریبوت آزموده شوند. Bot تست جدا از Bot تولیدی است؛ هیچ انتقال زودهنگام برای «امتحان‌کردن» مجاز نیست.

**M4 — برنامهٔ توقف نوشتن و مصرف:** پیش از cutover، سفارش و write جدید سیستم قدیمی باید در checkpoint مشخص freeze یا در delta journal قابل‌بازیابی ثبت شوند. مصرف نودها نیز هم‌زمان ادامهٔ بی‌حساب نداشته باشد؛ final receipt یا hold صریح نیاز است. زمان freeze، آخرین payment/update ID و مسئولیت هر صف ثبت شوند.

**M5 — تأیید مالک و تحویل انحصاری:** نسخه، backup، نتایج، دامنه و پورت، حق rollback و توقف احتمالی اتصال‌ها تأیید شوند. Agentها با هویت تازه و همان نگاشت منطقی؛ subscription endpoint و Bot receiver بعد از آماده‌بودن مقصد تحویل داده شوند. old/new نباید هم‌زمان یک Bot token را poll یا یک پرداخت را اعمال کنند.

**M6 — کنترل پس از انتقال:** خرید، تمدید، ساب قدیمی، کاربر Restore، نماینده، چند نود و مجموع حسابداری از مسیر واقعی بررسی شوند. endpoint قدیمی، backup و نگاشت rollback تا تأیید نهایی قابل‌بازیابی بمانند؛ حذف فوری سرور قدیمی بخشی از این طرح نیست.

## ۵. پورت، دامنه و Rollback

**عدد پورت عمومی قدیمی هنوز در این بررسی از تنظیمات تولیدی تأیید نشده است.** مقدار `127.0.0.1:2087` backend آزمایش PRO است، نه مدرک پورت عمومی قدیمی. تنظیمات واقعی Nginx/CLI/URL قدیمی باید به‌صورت read-only بررسی و مقدار همان قرارداد در migration manifest ثبت شود. تا آن زمان فیلد عددی آن `null` است؛ پیش‌فرض 443 یا 2087 یا 9090 جای اثبات را نمی‌گیرد. مقصد نهایی باید پورت عمومی موردنیاز قبلی را حفظ کند.

DNS فقط یکی از اجزای cutover است. گواهی، hostname/port/path، pin و چرخهٔ تمدید Agent، Bot webhook، Mini App و مشتریان کش‌شده نیز نیازمند برنامه‌اند. تغییر گواهی بدون مسیر اعتماد معتبر نمی‌تواند با غیرفعال‌کردن TLS verification رفع شود.

Rollback دیتابیس با Rollback کانفیگ Xray فرق دارد. اگر پس از cutover پرداخت، تمدید یا مصرف جدید ثبت شده باشد، برگرداندن backup قدیمی یا DNS به‌تنهایی داده را گم می‌کند. پیش از بازگشت باید writeها مهار، deltaهای جدید و cursorهای Bot تطبیق داده و target مصرف نهایی مشخص شود. اگر این تطبیق ممکن نیست، ورود به حالت read-only/توقف امن مجاز است؛ rollback خودکار با حذف رویداد تازه مجاز نیست.

## ۶. شرط پایان

همهٔ گیت‌های acceptance سند همراه باید برای همان نسخه و مجموعهٔ capability واقعاً موردنیاز تأیید شوند. WARP/AdBlock طبق تصمیم PRO منتقل نمی‌شوند؛ licensing و توسعهٔ غیرمرتبط ربات فعلاً عقب‌اند، ولی **کارکرد فعلی ربات‌ها، نمایندگان و حفظ اطلاعاتشان از شروط اجباری انتقال‌اند**. نقص در هر قلمرو اجباری، مخفی‌کردن موارد به‌عنوان «بعداً» یا تأیید صوری ممنوع است.
