# کنترل بکاپ بومی از پنل مالک — نسخهٔ ۱، فقط PRO LAB

این مرحله، ساخت آرشیو بومی رمز‌شده، دانلود مستقیم، زمان‌بندی روزانه/هفتگی و
retention را به صفحهٔ `/backups` مالک متصل می‌کند. قالب آرشیو، بررسی سازگاری
و restore قرنطینه‌شده همان [هستهٔ بکاپ آفلاین](native-backup-v1.fa.md) است.
این تحویل به‌تنهایی گیت [Backup/Restore #4](https://github.com/darktunnelmika/dark-xray-pro/issues/4)
یا M03 را کامل نمی‌کند.

## رفتار مالک

- ایجاد بکاپ یک job پایدار می‌سازد. شناسهٔ درخواست تا مشخص‌شدن نتیجه حفظ
  می‌شود؛ قطع پاسخ، refresh یا ارسال دوبارهٔ همان درخواست بکاپ دوم نمی‌سازد.
- زمان‌بندی، منطقهٔ زمانی IANA، ساعت محلی و روز هفته دارد. پیش‌فرض خاموش است؛
  مقدار اولیه روزانه ساعت `03:00` در `Asia/Tehran` است. تنظیمات با revision
  مقایسه می‌شوند و ویرایش هم‌زمان، تغییر مالک دیگر را بی‌خبر بازنویسی نمی‌کند.
- پس از خاموشی زمان‌بند، حداکثر یک نوبت عقب‌افتاده ساخته می‌شود. رسید نوبت
  زمان‌بندی پس از restart نیز باقی می‌ماند؛ ساعت تابستانی یا ویرایش retention
  نباید یک نوبت را دوباره ایجاد کند.
- دانلود یک جریان مستقیم است و آرشیو را کامل در RAM سرور یا browser blob
  قرار نمی‌دهد. اعتبار نشست و نقش مالک پیش از بازکردن جریان بررسی می‌شوند.
  بستن جریان، pin آن را آزاد می‌کند.
- پیش‌فرض retention برابر نگه‌داری ۷ نسخه و ۳۰ روز است. آخرین آرشیو موفق،
  آخرین نسخه با restore واقعاً تأییدشده و دانلودهای جاری محافظت می‌شوند.
  فایل ناشناخته یا انتشار بدون رسید معتبر، موفق فرض یا خودکار حذف نمی‌شود.
  پاک‌سازی پس از ساخت انجام می‌شود و محافظت نسخه‌ها اولویت دارد؛ تعداد
  موجود ممکن است از مقدار تنظیم‌شده بیشتر باشد. مثلاً نگه‌داری ۷ نسخه می‌تواند
  پس از تکمیل بکاپ تازه، تا نوبت بعدی ۸ نسخه باقی بگذارد.
- بارگذاری فایل رمز‌شده در [صندوق جداگانهٔ upload](native-backup-upload-v1.fa.md)
  پیاده‌سازی شده است؛ capability آن فقط با صندوق سالم فعال می‌شود. قابلیت
  restore همچنان `false` است. کلید خصوصی بازیابی در پنل، API یا تنظیمات worker وارد نمی‌شود.

### وقفهٔ واقعی پنل و لغو

ساخت نسخهٔ ۱ به توقف HUB نیاز دارد. قفل وضعیت تا پایان snapshot و رمزگذاری
نگه داشته می‌شود؛ بنابراین اندازهٔ داده و سرعت دیسک در مدت وقفه مؤثرند.
این مسیر، بکاپ آنلاین یا توقف با زمان ثابت نیست.

در فاصلهٔ توقف، API پنل نیز در دسترس نیست. رابط آخرین وضعیت دریافت‌شده را
نگه می‌دارد و دوباره متصل می‌شود؛ درصد پیشرفت، phase تازه یا دریافت لغو را
حدس نمی‌زند. لغو از مرورگر پیش از وقفه یا پس از بازگشت API قابل تحویل است.
worker لغو تحویل‌شده را مستقل از عمر درخواست HTTP ثبت و پردازش می‌کند و
وظیفهٔ روشن‌کردن HUB را با لغو یا قطع ارتباط کنار نمی‌گذارد.

انتقال‌های جاری (دانلود و upload) قبل از ثبت قصد توقف تخلیه می‌شوند. اگر انتقال ادامه داشته
باشد، job اجازه ندارد HUB را خاموش کند. شروع انتقال تازه نیز در طول اجرای
job یا بازیابی سرویس رد می‌شود. این قاعده دانلود مالک را وسط جریان با یک
بکاپ زمان‌بندی‌شده قطع نمی‌کند.

## تفکیک تأییدها

| وضعیت | شاهد واقعی |
| --- | --- |
| `checksum_verified` | ایجاد بادوام فایل، رسید معتبر و hash مستقل ciphertext منتشرشده |
| `restore_verified` | برای این نسخه از worker تولید نمی‌شود؛ به آزمون مستقل بازیابی نیاز دارد |
| `publication_unknown` | فایل یا رسید به نتیجهٔ قابل‌اعتماد نرسیده است؛ موفقیت اعلام و فایل کورکورانه حذف نمی‌شود |
| `recovery_required` | بازگشت HUB هنوز تأیید نشده؛ job جدید اجرا نمی‌شود و وظیفهٔ بازیابی باقی می‌ماند |

گیرندهٔ عمومی `age` فقط برای رمزگذاری کافی است. برابر بودن checksum جای
رمزگشایی، اعتبارسنجی دیتابیس یا آزمودن restore را نمی‌گیرد. آزمون عملیاتی
restore با identity خصوصیِ خارج از worker، در مقصد تازه و قرنطینه‌شده انجام
می‌شود و سرویس بازیابی‌شده را فعال نمی‌کند.

## مرز اعتماد و فرایند مستقل

`dark-pro-backup-worker` یک سرویس جدا از `dark-xray-pro-lab.service` است.
HUB تنها درخواست مالک را به Unix socket ثابت می‌فرستد؛ خودش فرمان systemd
یا child بکاپ اجرا نمی‌کند. worker پیش از توقف، وظیفهٔ بازگشت سرویس و وضعیت
فعال قبلی را در journal بادوام ثبت می‌کند. startup recovery و `ExecStopPost`
برای ادامهٔ همین وظیفه‌اند. PID ذخیره‌شده مبنای کشتن فرایند در restart نیست.

| منبع | مسیر ثابت |
| --- | --- |
| تنظیمات خصوصی root | `/etc/dark-xray-pro-backup-worker/config.json` |
| journal مستقل | `/var/lib/dark-xray-pro-backup-worker` |
| کنترل محلی | `/run/dark-xray-pro-backup-worker/control.sock` |
| آرشیوها | `/var/backups/dark-xray-pro-native` |
| سرویس هدف | `dark-xray-pro-lab.service` |

اتصال محلی با peer credentials به root و UID واقعی HUB محدود است. API فقط
عملیات شناخته‌شده، event ID و تنظیمات محدود را می‌پذیرد. نام unit، shell،
مسیر، binary، URL، environment یا کلید خصوصی از مرورگر دریافت نمی‌شود.
هویت actor از نشست امضاشدهٔ مالک می‌آید. مسیرها روی listener Agent ثبت
نمی‌شوند؛ bearer قدیمی مجوز ورود به API مرورگر نیست.

فایل config نسخهٔ ۱، path/hash/revision ثابت دو باینری HUB و backup، گیرندهٔ
عمومی و سقف حجم/زمان را تعیین می‌کند. worker قبل از ساخت، هویت فایل اجرایی،
مالکیت و مجوز مسیرها، آدرس میزبان LAB، محیط سرویس، فضای دیسک و inventory را
بررسی می‌کند. اجرای inbound یا هماهنگی مصرف چندنودی در این نسخه پشتیبانی
نمی‌شود و preflight آن را رد می‌کند.

پیش از توقف HUB، preflight همان باینری pin‌شدهٔ backup را با UID/GID کاربر
LAB و گروه‌های تکمیلی خالی، بدون آرگومان اجرا می‌کند. این مسیر فقط خطای
استفادهٔ CLI را برمی‌گرداند و به داده یا خروجی بکاپ دست نمی‌زند. مهلت اجرای
آن ۱۰ ثانیه است؛ پس از پایان مهلت، پاک‌سازی محدود گروه فرایند انجام می‌شود.
اگر تغییر هویت یا اجرای child ممکن نباشد، job پیش از
توقف پنل ناموفق می‌شود. این بررسی به مسیر مستقل بازگرداندن HUB وابسته نیست.

ابزار backup با UID/GID غیر root متعلق به HUB، گروه‌های تکمیلی خالی و محیط
حداقلی اجرا می‌شود. خروجی ابتدا در پوشهٔ خصوصی همان job ساخته می‌شود و سپس
به کپی root-owned مستقل تبدیل می‌شود؛ تغییر مالکیت یک فایلِ هنوز باز به‌تنهایی
برای محافظت از آرشیو کافی فرض نمی‌شود. فضای لازم برای staging و انتشار در
بودجهٔ دیسک حساب می‌شود.

## فعال‌سازی و ارتقای LAB

سه gate موجود `DARK_PRO_LAB_MODE=1`،
`DARK_PRO_ENABLE_BUSINESS_CORE=1` و `DARK_PRO_ENABLE_OFFLINE_BACKUP_V1=1`
پیش‌نیاز gate جدید `DARK_PRO_ENABLE_BACKUP_CONTROL_V1=1` هستند. مقدار نامعتبر
یا پیش‌نیاز ناقص شروع HUB را رد می‌کند. نبودن worker، HUB سالم را خاموش نمی‌کند؛
درخواست کنترل خطای صریح unavailable می‌گیرد.

بستهٔ CI اکنون باینری پنجم worker و unit مرجع آن را نیز با checksum شامل
می‌شود. نصب باید از artifact دارای commit/tree و checksum تأییدشده باشد.
تنظیمات root، مقصد آرشیو و service unit پیش از روشن‌شدن worker آماده می‌شوند.
مسیرهای مجاز HTTPS در [snippet مستقل nginx](../ops/nginx/native-backups.conf)
محدود به route، method و ID دقیق‌اند؛ قانون گسترده برای `/api/` اضافه نمی‌شود.

unit سیستم عمداً `User=root` را تعیین نمی‌کند؛ هویت پیش‌فرض سرویس سیستم root
است و worker نیز EUID صفر را بررسی می‌کند. در مسیر تنظیم credentials و
seccomp در [systemd](https://github.com/systemd/systemd/blob/v255/src/core/exec-invoke.c)،
تعیین صریح این کاربر همراه با `NoNewPrivileges=yes` می‌تواند `CAP_SETUID` را
از permitted/effective حذف کند، حتی اگر در bounding set باشد. این رفتار در
LAB با systemd 255 بازتولید شد. حذف همین تعیین اضافی، تغییر هویت child را
با همان bounding set و ambient/inheritable خالی ممکن می‌کند. محدودیت نوشتن
وضعیت مبدأ، seccomp و `NoNewPrivileges` حفظ می‌شوند؛ CLI همچنان غیر root است.

`scripts/install-lab.sh` همچنان فقط برای سرور تازه و خالی است. ارتقای LAB
موجود با release نسخه‌دار، snapshot تنظیمات و مقایسهٔ منطقی دیتابیس انجام
می‌شود. بازگشت خودکار فقط binary و تنظیمات را برمی‌گرداند؛ دیتابیس مالی
موجود reset یا با snapshot قبلی جایگزین نمی‌شود. زمان‌بندی تا انتخاب مالک
خاموش و owner report bot غیرفعال می‌ماند.
