# بارگذاری بکاپ رمزگذاری‌شده از پنل مالک — نسخهٔ ۱، فقط PRO LAB

صفحهٔ `/backups` اکنون بخش جداگانهٔ «بارگذاری نسخهٔ رمزگذاری‌شده» دارد.
مالک می‌تواند فایل قبلاً دانلودشده را ارسال کند، نتیجهٔ ثبت‌شده را ببیند،
ارسال قطع‌شده را با همان شناسه از ابتدا تکرار کند و فایل کامل را مستقیم
دانلود کند. حذف صریح فقط نسخهٔ موجود در صندوق بارگذاری را حذف می‌کند.

این مرحله ادامهٔ [کنترل بکاپ بومی](native-backup-controls-v1.fa.md) است.
فایل‌های ورودی وارد تاریخچهٔ بکاپ‌های ساخته‌شده یا retention آن نمی‌شوند.
گیرندهٔ عمومی یا header فایل، سازگاری محتوای رمز‌شده را ثابت نمی‌کند؛ بنابراین
قابلیت `restore` همچنان `false` است و هیچ کلید خصوصی در مرورگر، API یا
backup worker پذیرفته نمی‌شود. گیت کامل M03، بازیابی عملیاتی و مهاجرت با این
تحویل کامل اعلام نمی‌شوند؛ وضعیت اداری issue، جای شواهد پذیرش را نمی‌گیرد.

## آنچه مالک می‌بیند

1. مرورگر فایل را در worker جدا و بخش‌های یک MiB می‌خواند و SHA-256 کامل را
   محاسبه می‌کند. لغو در این مرحله هیچ فایلی به سرور نمی‌فرستد.
2. پیش از درخواست تخصیص، شناسهٔ درخواست، اندازه و hash در همان زبانه ذخیره
   می‌شوند. فایل، کلید و اعتبارنامه در این رسید مرورگر ذخیره نمی‌شوند.
3. سرور تخصیص را به actor واقعی نشست مالک، event، اندازه و SHA-256 متصل
   می‌کند. تغییر محتوا زیر event قبلی تعارض است.
4. مرورگر `File` را مستقیم ارسال می‌کند. پیشرفت ارسال مرورگر با رسید ذخیرهٔ
   سرور متفاوت نمایش داده می‌شود. پایان ارسال به‌تنهایی پیام موفقیت نیست.
5. پس از ثبت بادوام فایل و تطبیق مستقل hash، وضعیت `received` نمایش داده
   می‌شود. دانلود از پیوند مستقیم و احراز‌شده انجام می‌شود.

پس از refresh، شناسهٔ قبلی بررسی می‌شود؛ فایل خودکار دوباره فرستاده نمی‌شود.
برای تکرار ارسال قطع‌شده باید همان فایل را انتخاب کرد و hash کامل آن دوباره
تطبیق داده شود. ادامه از offset میانی در نسخهٔ ۱ وجود ندارد؛ تلاش تازه از
ابتدای فایل و با همان تعهد اندازه/hash شروع می‌شود. تخصیص کامل‌شده فقط رسید
قبلی را برمی‌گرداند و فایل آن بازنویسی نمی‌شود.

| وضعیت | معنی |
| --- | --- |
| `awaiting_upload` | تخصیص ثبت شده و منتظر فایل است |
| `receiving` | دریافت واقعی بایت‌ها ادامه دارد؛ نسخهٔ قابل دانلودی منتشر نشده |
| `checking` | دریافت تمام شده و ثبت نهایی/بازخوانی مستقل در حال بررسی است |
| `received` | اندازه و SHA-256 فایل رمز‌شده با تعهد اولیه برابر و ذخیره بادوام است |
| `interrupted` | ارسال یا ذخیره قطع شده؛ تکرار صریح از ابتدا ممکن است |
| `rejected` | اندازه، hash یا header عمومی فایل پذیرفته نشده |
| `cancelled` | لغو ثبت شده؛ این تخصیص دوباره قابل ارسال نیست |
| `deleting` / `deleted` | قصد حذف/حذف نسخهٔ صندوق ثبت شده؛ رسید قدیمی حفظ می‌شود |
| `publication_unknown` | انتشار فایل نتیجهٔ قطعی ندارد؛ فایل و شاهد حفظ می‌شوند و بررسی اپراتور لازم است |

تنها برچسب موفقیت این صندوق `ciphertext_checksum_verified` است.
manifest بومی، نسخهٔ schema، تعداد مشتریان، اندازهٔ بازشده و اعتبارسنجی
بازیابی از فایل رمز‌شده حدس زده نمی‌شوند. حتی یک فایل age غیر بومی می‌تواند
از بررسی عمومی header و انتقال سالم عبور کند؛ این نتیجه مجوز restore نیست.

## محدودیت‌ها و حفاظت از ذخیره‌سازی

| حد | نسخهٔ ۱ |
| --- | --- |
| اندازهٔ هر فایل | حداکثر ۶۶ GiB رمز‌شده |
| مجموع رزرو صندوق | حداکثر ۱۳۲ GiB |
| حاشیهٔ فضای آزاد | حداقل ۲۵۶ MiB؛ پیش از تخصیص و حین دریافت کنترل می‌شود |
| تخصیص‌های حذف‌نشده | حداکثر ۳۲ |
| رسیدهای مادام‌عمر صندوق | حداکثر ۴۰۹۶؛ حذف فایل، رسید را حذف نمی‌کند |
| دریافت هم‌زمان | یک فایل |
| بافر کپی/بازخوانی سرور | حداکثر ۶۴ KiB |
| مهلت بی‌حرکتی دریافت | ۶۰ ثانیه، به‌صورت لغزان |
| مهلت کل درخواست ارسال | ۶ ساعت |

مسیر ثابت صندوق، `/var/lib/dark-xray-pro-backup-worker/uploads`، متعلق به
root و خصوصی است. journal آن از `control.json` موجود جداست؛ برگشت باینری
قدیمی به تغییر قالب تاریخچهٔ بکاپ وابسته نیست. هیچ مسیر، نام فایل اجرایی،
دستور، URL، مقصد restore یا identity از ورودی مالک گرفته نمی‌شود.

هر تلاش در فایل خصوصی همان ID نوشته می‌شود. دریافت اندازهٔ دقیق، EOF،
SHA-256 و header عمومی محدود بررسی می‌شود. فایل قبل از انتشار sync شده،
با `RENAME_NOREPLACE` منتشر و پوشه sync می‌شود؛ سپس فایل نهایی مستقلاً hash
می‌شود و رسید موفق در journal بادوام ثبت می‌شود. نام فایل از ورودی مرورگر
نمی‌آید. symlink، hardlink، فایل غیرعادی و عضو ناشناختهٔ پوشه پذیرفته نمی‌شوند.

لغو، قصد خود را پیش از قطع خواندن ثبت می‌کند. اتصال قطع‌شده و مرگ فرایند،
فایل ناقص قابل دانلود نمی‌سازند. restart می‌تواند وضعیت قطع‌شده را مشخص کند؛
انتشار نامطمئن را صرفاً به‌خاطر restart موفق اعلام نمی‌کند. نسخهٔ کامل
منتشرشده با خطای تأیید دوام حفظ می‌شود. پاک‌سازی فقط فایل‌های شناخته‌شدهٔ
همان ID را حذف می‌کند و پوشهٔ ناشناخته را بازگشتی پاک نمی‌کند.

حذف نسخهٔ دانلودشونده تا بسته‌شدن جریان رد می‌شود. رسید `deleted` باقی
می‌ماند و تکرار event، فایل تازه‌ای زیر همان هویت نمی‌سازد. فایل‌های لغوشده
یا قطع‌شده تا حذف صریح همچنان از ظرفیت رزروشده استفاده می‌کنند.

## احراز هویت و اتصال به worker

مسیرهای browser فقط نشست امضاشدهٔ مالک را می‌پذیرند. تغییرات همچنان به
Origin معتبر، Fetch-Site مناسب و CSRF نیاز دارند. فقط route دقیق `content`
از `application/octet-stream` استفاده می‌کند؛ سایر mutationها JSON هستند.
نماینده، bearer قدیمی و listener نود به این قابلیت دسترسی ندارند.

| عملیات | مسیر نسبت به `/api/v1/workspace/owner/backups` |
| --- | --- |
| وضعیت صندوق / تخصیص | `GET /uploads` / `POST /uploads` |
| وضعیت یک تخصیص | `GET /uploads/{id}` |
| دریافت فایل با اندازه/hash ثابت | `PUT /uploads/{id}/content` |
| لغو / حذف صریح | `POST /uploads/{id}/cancel` / `POST /uploads/{id}/remove` |
| دانلود نسخهٔ کامل | `GET /uploads/{id}/download` |

کل مسیر انتقال، pin مشترک با دانلودهای بکاپ دارد. worker ابتدا شروع اجرای
بکاپ را ثبت می‌کند و سپس منتظر پایان انتقال‌های قبلی می‌ماند؛ در این فاصله
انتقال تازه پذیرفته نمی‌شود. pin ارسال تا flush رسید کامل از HUB به مالک
حفظ می‌شود. بازخوانی رسید کامل‌شده روی اتصال مستقل بدون body انجام می‌شود
تا پاسخ زودهنگام HTTP، pin را پیش از پاسخ HUB آزاد نکند.

nginx فقط routeها و methodهای دقیق را مجاز می‌کند. درخواست فایل بدون
buffering به HUB می‌رسد تا احراز هویت پیش از spool شدن یک آرشیو بزرگ انجام
شود. درخواست ارسال خودکار توسط proxy تکرار نمی‌شود. محدودیت‌های کوتاه API
عادی برای این مسیر به مهلت‌های محدود انتقال تبدیل شده‌اند؛ سراسری حذف نشده‌اند.

## شواهد آزمون و مرز باقی‌مانده

- آزمون store، اندازه/hash اشتباه، فایل ناقص/اضافی، لغو، تکرار، فشار دیسک،
  symlink/hardlink، انتشار بدون جایگزینی، خطای sync، tombstone و بازیابی
  پس از `SIGKILL` واقعی را بررسی می‌کند.
- آزمون واقعی HTTP و Unix socket، عبور انتقال از مهلت معمول API، لغو
  خواندن متوقف‌شده و ماندن pin تا بسته‌شدن رسید/دانلود را بررسی می‌کند.
- آزمون مرورگر، hash تکه‌ای، قطع/بازخوانی رسید، انتخاب فایل متفاوت، لغو،
  ظرفیت پر و نمایش فارسی ۳۲۰ پیکسل در هر دو پوسته را بررسی می‌کند.
- آزمون opt-in صندوق، **۳٬۲۲۱٬۲۳۷٬۸۱۷ بایت واقعی روی دیسک** را دریافت و
  مستقل بازخوانی می‌کند. CI یک فرایند مستقل را با سقف peak RSS برابر ۱۲۸ MiB
  می‌سنجد. این fixture عمداً payload رمز‌شدهٔ ساختگی است و شاهد اعتبارسنجی
  age، دیتابیس SQLite چندگیگابایتی یا بازیابی بومی نیست.

پذیرش عملیاتی باید یک بکاپ واقعی LAB را از HTTPS مالک آپلود و دانلود کند،
hash را با نسخهٔ مبدأ تطبیق دهد، سپس با CLI pin‌شده و identity خصوصی خارج از
worker، `verify`، `inspect` و restore در مقصد غایب و خصوصی را اجرا کند.
مقایسهٔ مالی restore با baseline همان آرشیو انجام می‌شود. یک baseline جدا
پس از ورود جدید مالک، ثابت‌ماندن دیتابیس جاری را می‌سنجد؛ ردیف نشست تازه
دلیل مجاز برای جایگزینی دیتابیس یا دست‌کاری baseline قبلی نیست.

کنترل خودکار رمزگشایی/restore از UI، فعال‌سازی نصب بازیابی‌شده، storage بیرونی،
آزمون SQLite بزرگ واقعی، تسویهٔ ناوگان و مهاجرت Dark Restore همچنان مسیرهای
مجزای بعدی هستند. owner report bot خاموش می‌ماند و خروجی restore قرنطینه است.
rollback نصب فقط binary/config را برمی‌گرداند؛ دیتابیس مالی reset یا جایگزین
نمی‌شود.
