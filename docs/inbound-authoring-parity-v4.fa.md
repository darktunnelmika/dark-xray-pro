# ایجاد اینباند: مقصد مستقل، پروتکل، انتقال و امنیت — نسخهٔ ۴

این تغییر چهار ایراد فرم ایجاد اینباند را به‌صورت یک مسیر مشترک UI، API، ذخیره‌سازی
و تولید کانفیگ اصلاح می‌کند. مرجع مقایسه،
[سنایی v3.10.2](https://github.com/MHSanaei/3x-ui/tree/v3.10.2) و موتور پین‌شدهٔ آن،
[Xray commit 701af60772cd](https://github.com/XTLS/Xray-core/commit/701af60772cda123492f86e383e1fdba066614a9)،
با شناسهٔ نسخهٔ `26.10.10` است. پیاده‌سازی این مخزن مستقل است.

## مقصد ایجاد

«HUB — this server» یک مقصد صریح در انتخاب نود است. شناسهٔ `hub-local` رزرو شده
و شناسهٔ نصب آن از کلید پایدار همین نصب مشتق می‌شود. هاب در Registry نودهای جفت‌شده
و شمارندهٔ نودهای آنلاین وارد نمی‌شود. انتخاب یک نود بیرونی فقط همان مقصد را وارد
کانفیگ می‌کند؛ هاب پیش‌فرض انتخاب نشده و ضمنی افزوده نمی‌شود.

Direct، Tunnel و منبع/مقصد Dark Swap همچنان مستقل‌اند. در مسیر UDP، رله نیز نوع
ترافیک همان پروتکل را حمل می‌کند. Collision، هویت نصب، پورت‌های رزروشده و چرخهٔ
Swap پیش از ذخیره کنترل می‌شوند.

## پروتکل و انتقال

انتخاب «پروتکل» در بخش اتصال قرار دارد و تنظیمات وابسته به آن تغییر می‌کنند.

| پروتکل/نوع اینباند | مسیر تولید تنظیمات |
| --- | --- |
| VMess، VLESS، Trojan | تنظیمات بومی Xray و حساب‌های متعلق به business |
| Shadowsocks و روش‌های 2022 | تنظیمات بومی و کلیدهای مستقل کاربر |
| WireGuard | کلید سرور و peer، آدرس پایدار و خروجی WireGuard |
| Hysteria2 | انتقال اختصاصی QUIC و TLS |
| HTTP و Mixed | حساب‌های مدیریت‌شده؛ Mixed شامل SOCKS/HTTP |
| Tunnel / Dokodemo-door | مقصد و نگاشت پورت؛ بدون حساب کاربر |
| TUN | رابط و مسیریابی؛ بدون حساب کاربر |
| MASQUE | تنظیمات اختصاصی بومی و TLS/QUIC |
| MTProto | کانفیگ و manifest آداپتور MTProto/FakeTLS |
| AmneziaWG | کانفیگ و manifest آداپتور، peer و خروجی کلاینت |
| TUIC v5 | کانفیگ و manifest آداپتور مستقل از Xray |

منوی «انتقال» برای پروتکل‌های عمومی هفت انتخاب دارد: RAW/TCP، mKCP، WebSocket،
gRPC، HTTPUpgrade، XHTTP و XDrive. RAW و TCP یک انتخاب‌اند. پروتکل‌های اختصاصی
منوی نامرتبط دریافت نمی‌کنند. تنظیمات انتقال، Sockopt، FinalMask، QUIC، XMUX و
تنظیمات کلاینت با نام و نوع واقعی موتور ذخیره می‌شوند. انتخاب‌های قبلی در draft
فرم قابل برگشت‌اند؛ payload فقط بخش‌های فعال و سازگار را ارسال می‌کند.

خروجی URI تنها در فرمت‌هایی ساخته می‌شود که قرارداد واقعی دارند؛ XDrive و MASQUE
خروجی JSON دارند. renderer و exporter خطای صریح برای فرمت یا ویژگی پشتیبانی‌نشده
می‌دهند. گزینهٔ MUX مربوط به خروجی کلاینت است و با Mux سرور اشتباه گرفته نمی‌شود.

## امنیت و ابزارها

REALITY شامل هدف و SNI، Short ID، X25519، ML‑DSA‑65، fingerprint، SpiderX، نسخهٔ
کلاینت، اختلاف زمان، Xver، گزارش کلید و محدودیت fallback است. TLS شامل چند گواهی
inline یا مسیر فایل، نسخه‌ها، ALPN، cipher/curve، سیاست SNI و ریشه‌ها، session
resumption، ECH و تنظیمات اعتماد کلاینت است.

ابزارهای مالک زیر با session، Origin و CSRF محافظت می‌شوند:

- تولید X25519 و تولید واقعی ML‑DSA/ECH با فایل اجرایی پین‌شده و SHA-256؛
- بررسی گواهی، هش DER/SPKI و تولید گواهی self-signed با SAN؛
- بررسی یک هدف و یافتن هدف از preset، فهرست مشخص یا CIDR عمومی محدود؛
- دریافت گواهی مقصد از همان مسیر بررسی TLS؛
- انتخاب مبدأ واقعی هاب یا نود، نمایش مبدأ در نتیجه و لغو درخواست.

اسکن فقط با اقدام صریح آغاز می‌شود. DNS پیش از اتصال بررسی و IP مقصد پین می‌شود؛
نشانی خصوصی، loopback، مقصد mixed public/private و تغییر مقصد در DNS اجازهٔ عبور
ندارند. CIDR حداکثر ۲۵۶ نشانی و فهرست صریح حداکثر ۳۲ هدف دارد. نتیجهٔ TLS1.3/h2/
X25519، گواهی و latency، اثبات اتصال کامل REALITY نیست. قطع یا جایگزینی نود نتیجهٔ
هاب را به نام آن نود برنمی‌گرداند.

تولید ML‑DSA/ECH در نصب با متغیرهای `DARK_PRO_AUTHORING_CORE_PATH` و
`DARK_PRO_AUTHORING_CORE_SHA256` فعال می‌شود. این helper از موتور آزمایشی حسابداری
جداست. SHA پیش از اجرای همان فایل بازشده کنترل می‌شود و ورودی مرورگر امکان تغییر
مسیر، فرمان یا checksum را ندارد.

## نگهداری امن و سازگاری

`profile.spec` قرارداد نسخه‌دار خصوصی است. API عمومی از نسخهٔ redacted همراه
`spec_secret_paths` استفاده می‌کند؛ وجود راز مشخص می‌شود و مقدار آن بازگردانده
نمی‌شود. نبودن فیلد هنگام ویرایش، راز ذخیره‌شده را حفظ می‌کند؛ مقدار صریح خالی آن
را پاک می‌کند و در صورت ضروری‌بودن فیلد، validation ذخیره را رد می‌کند.

ردیف‌های گواهی و FinalMask شناسهٔ پایدار دارند تا حذف، جابه‌جایی یا تغییر نوع، راز
ردیف دیگری را منتقل نکند. این شناسه‌ها وارد کانفیگ موتور نمی‌شوند. کلیدها، PEM،
مسیر گواهی/کلید و دادهٔ حساس template/header در پاسخ، receipt عمومی یا preview
نیستند. private profile در envelope رمز‌شدهٔ v6 و plan در envelope v4 نگه‌داری
می‌شود؛ binary قدیمی که این قرارداد را نمی‌شناسد داده را به نسخهٔ ضعیف‌تر تبدیل
نمی‌کند. فرم قدیمی برای پروفایل‌های قدیمی باقی می‌ماند و نمی‌تواند spec جدید را
با یک ویرایش scalar حذف کند.

## دامنهٔ پذیرش

تمام ۱۴ نوع، fixture مستقل دارند و ذخیره/بازکردن بدون ساخت مشتری یا target runtime
آزمایش می‌شود. موتور پین‌شده تنظیمات ۱۱ نوع بومی، هفت انتقال و ماتریس TLS/REALITY
سرور و کلاینت را با `run -test` می‌پذیرد. این آزمون کانفیگ است و هیچ listener عمومی
یا اتصال خارجی ایجاد نمی‌کند. ابزارهای امنیت با TLS محلی واقعی، آزمون Scope، DNS،
لغو، محدودیت کار و کلیدساز واقعی بررسی می‌شوند. رابط فارسی/انگلیسی و موبایل، حفظ
راز و save/reopen نیز آزمون مرورگر دارند.

ایجاد طرح همچنان `SAVED_DISABLED` و `runtime_apply=false` است. اعتبارسنجی یک
پروتکل نیازمند حساب، از هویت ثابت و موقت مخصوص بررسی کانفیگ استفاده می‌کند؛ این
هویت در DB، profile ذخیره‌شده، مشتریان یا delivery قرار نمی‌گیرد. تولید تنظیمات
آداپتور MTProto/AmneziaWG/TUIC، نصب و supervise کردن موتورهای خارجی نیست. فعال‌سازی
ترافیک، حسابداری، publication اشتراک و گیت‌های Apply دامنهٔ پذیرش جداگانه دارند؛
این فرم آن‌ها را ضمنی فعال نمی‌کند. هیچ migration یا تغییر روی سرویس قدیمی انجام
نمی‌شود.

Promotion آزمایشی موجود فقط قرارداد محدود پروفایل‌های legacy با TCP/REALITY و
نود loopback رزروشده را می‌پذیرد. طرح‌های `spec` جدید، حتی VLESS/TCP/REALITY ساده،
تا پذیرش جداگانهٔ زنجیرهٔ اجرا و اشتراک با blocker صریح `profile.spec` متوقف می‌شوند.
آزمون موفق مسیر legacy و آزمون رد بدون تغییر داده برای مسیر جدید مستقل باقی می‌مانند.
