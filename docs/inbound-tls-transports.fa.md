# TLS، WebSocket و HTTP Upgrade در ساخت اینباند

این مرحله، ادامهٔ [تنظیمات شبکه و Host](inbound-network-endpoints.fa.md) است.
ساخت پلن اکنون دو نوع امنیت دارد: REALITY با کلید تولیدشدهٔ سرور، و TLS با
گواهی و کلید واردشده توسط مالک. داده‌های TLS در فرم، اعتبارسنجی، ذخیرهٔ
رمز‌شده، بازخوانی، renderer و codec به یک قرارداد متصل‌اند.

ذخیره همچنان یک پلن غیرفعال می‌سازد. این تغییر، مرز حسابداری اجرای نود یا
انتشار اشتراک مشتری را باز نمی‌کند. پشتیبانی renderer و codec به‌تنهایی
به معنی فعال‌شدن مسیر عمومی تحویل اشتراک نیست.

ادامهٔ مسیر اجرایی در [آماده‌سازی طرح برای اجرای حسابداری‌شده](inbound-plan-activation.fa.md)
ثبت شده است. پذیرش اولیهٔ آن فقط Direct TCP/REALITY در LAB ایزوله است؛
پشتیبانی TLS این سند همچنان مربوط به ساخت، ویرایش، رندر و آزمون مستقل اتصال است.

## ترکیب‌های پشتیبانی‌شده

| شبکه | REALITY | TLS | گزینه‌های شبکه |
| --- | --- | --- | --- |
| TCP | بله | بله | Vision؛ نام سرویس ندارد. |
| gRPC | بله | بله | Service Name، Authority و Gun/Multi. |
| XHTTP | بله | بله | Path، Host، Mode و بازهٔ Padding تایپ‌شده. |
| WebSocket | خیر | بله | Path و Host. |
| HTTP Upgrade | خیر | بله | Path و Host. |

TLS در این قرارداد با حداقل TLS 1.3 رندر می‌شود. ALPN بر اساس شبکه تعیین
می‌شود: `h2` برای gRPC/XHTTP، `http/1.1` برای WebSocket/HTTP Upgrade، و
`h2,http/1.1` برای TCP. گزینهٔ آزاد ALPN، `allowInsecure`، مسیر فایل سرور،
Header دلخواه و JSON آزاد اضافه نشده‌اند.

Path جدید یک مسیر ASCII شروع‌شده با `/` و حداکثر ۲۰۴۸ بایت است؛ authority،
query، fragment، percent escape، backslash و فاصله پذیرفته نمی‌شود. این
محدودیت، تفاوت تفسیر URL در دو transport را حذف می‌کند. Host یک نام DNS
یا IPv4 بدون پورت و bracket است؛ تنظیم آدرس عمومی IPv6 در دارک‌سواپ همچنان
مجاز است. Host شبکه با آدرس عمومی اتصال و SNI سه فیلد مستقل است.

## جای کنترل‌ها

چهار بخش اصلی فرم همان **اتصال، دارک‌سواپ، پیشرفته و بازبینی** هستند.
انتخاب امنیت و ورود گواهی در بخش اتصال است؛ فقط تنظیمات مرتبط با انتخاب
فعلی نمایش داده و ارسال می‌شود. TLS از مقصد پوششی REALITY، Short ID یا
SpiderX استفاده نمی‌کند. fingerprint مشتری برای TLS هم قابل تنظیم است.

انتخاب نود، Listen IP، روشن/خاموش مستقل Direct و Tunnel، پورت شنود، Hostهای
عمومی و تنظیمات مسیر Swap همگی در **دارک‌سواپ** باقی می‌مانند. انتخاب TLS
این کنترل‌ها را به بخش دیگری منتقل یا تکرار نمی‌کند. TLS برای نود مقصد
رندر می‌شود؛ واسط Swap نباید گواهی، کلید خصوصی یا شناسهٔ مشتری را دریافت کند.

Sniffing از قرارداد موجود استفاده می‌کند. Fallback این مرحله همچنان محدود
به قرارداد قبلی REALITY است؛ برای TLS، تا زمان تکمیل آزمون رفتار و حسابداری
مربوط، انتخاب قابل‌استفاده‌ای ارائه نمی‌شود.

## قرارداد گواهی و کلید

ورودی خصوصی فقط در درخواست بررسی یا ذخیرهٔ پلن وجود دارد:

```json
{
  "profile": {
    "security": "tls",
    "transport": "ws",
    "server_names": ["edge.example.org"],
    "options": {
      "websocket": {"path": "/socket", "host": "edge.example.org"}
    }
  },
  "tls_credentials": {
    "certificate_pem": "PEM certificate chain",
    "private_key_pem": "PEM private key"
  }
}
```

این مثال فقط قسمت TLS را نشان می‌دهد؛ درخواست کامل همچنان شناسهٔ رویداد،
revisionها، نودها و یادداشت تغییر دارد. `tls_credentials` عضو پروفایل عمومی
نیست و در Preview، پاسخ ذخیره، رسید، فهرست اینباندها یا بازخوانی پلن برنمی‌گردد.

اعتبارسنجی سرور شامل این موارد است:

- زنجیرهٔ PEM با ترتیب leaf و سپس صادرکننده‌ها؛ حداکثر ۸ گواهی و ۶۴ KiB.
- دقیقاً یک کلید خصوصی PEM، حداکثر ۱۶ KiB؛ PKCS#8، RSA یا EC پشتیبانی می‌شود.
- تطابق واقعی کلید با گواهی، نوع کلید پشتیبانی‌شده و محدودیت اندازهٔ RSA.
- ترتیب و امضای اعضای زنجیره، کاربرد مجاز سرور و تاریخ اعتبار تمام اعضا.
- پوشش همهٔ Server Nameهای انتخاب‌شده در SAN گواهی؛ گواهی wildcard می‌تواند
  نام‌های مشخص را پوشش دهد، ولی مقدار SNI انتخاب‌شده یک نام مشخص است.
- حداکثر ۱۰۲۴ نام DNS معتبر در metadata گواهی leaf، با قواعد ASCII و wildcard
  محدود به پیشوند `*.`؛ این نام‌ها در پاسخ عمومی و مرورگر نیز محدود می‌مانند.
- رد دادهٔ اضافی، بلوک ناشناخته یا تکراری، کلید رمزدار، جفت نامنطبق و
  تنظیمات مختص REALITY در پروفایل TLS.

اعتبارسنجی ساختاری ادعای اعتماد یک CA عمومی نمی‌کند و شبکه را برای دریافت
گواهی یا تکمیل chain فراخوانی نمی‌کند. مشتری همچنان گواهی را با قواعد اعتماد
خود بررسی می‌کند. آزمون loopback از CA خصوصی موقت و اعتماد صریح همان fixture
استفاده می‌کند؛ اعتبارسنجی گواهی مشتری غیرفعال نمی‌شود.

فهرست Server Name پلن، انتخاب‌های SNI در خروجی و Hostها را محدود می‌کند.
در TLS، `rejectUnknownSni` خود Core پوشش نام در گواهی را بررسی می‌کند؛
این گزینه فهرست دقیق Server Nameهای پلن را به یک فهرست مجاز مستقلِ handshake
تبدیل نمی‌کند. نام دیگری که همان SAN گواهی پوشش می‌دهد نیز ممکن است handshake
معتبر داشته باشد.

## ویرایش و تعویض گواهی

پس از ذخیره، فرم فقط مشخصات عمومی گواهی را نشان می‌دهد: SHA-256 گواهی leaf،
SHA-256 کلید عمومی، نام‌های DNS، شروع و پایان اعتبار و نوع کلید. PEM گواهی
یا کلید خصوصی بازخوانی نمی‌شود.

در ویرایش TLS، حذف فیلد `tls_credentials` یعنی حفظ دقیق کلید و گواهی ذخیره‌شده.
برای تعویض، مالک «تعویض گواهی و کلید» را انتخاب و هر دو مقدار را وارد می‌کند.
`null`، object خالی یا جفت ناقص درخواست حفظ یا حذف محسوب نمی‌شود و خطا دارد.
تعویض صریح، revision پروفایل را افزایش می‌دهد؛ تکرار دقیق همان رویداد، همان
رسید را برمی‌گرداند و افزایش دوباره ایجاد نمی‌کند. تغییر فقط transport می‌تواند
از گواهی ذخیره‌شده استفاده کند.

نوع امنیت پلن پس از ساخت ثابت است. ویرایش می‌تواند شبکه را در محدودهٔ امنیت
فعلی عوض کند؛ تبدیل REALITY به TLS یا برعکس در این مرحله عملیات جداگانه‌ای
نیست. کپی یک پروفایل TLS نیز کلید آن را کپی نمی‌کند و به ورود یک جفت تازه
برای اینباند جدید نیاز دارد.

گواهی منقضی‌شده همچنان قابل بازخوانی است تا مالک بتواند آن را تعویض کند.
تاریخ اعتبار هنگام Preview و ذخیرهٔ جدید دوباره بررسی می‌شود. بازپخش رسید
قدیمی یک ذخیرهٔ جدید نیست و محتوای تاریخی آن تغییر نمی‌کند.

مرورگر SHA-256 گواهی واردشده را محاسبه و metadata پیش‌نمایش را با آن تطبیق
می‌دهد. ذخیره فقط پس از تطبیق پاسخ بررسی مجاز است؛ رسید ذخیره باید همان
metadata تأییدشده را داشته باشد. پاسخ دارای فیلد خصوصی یا PEM رد می‌شود.
مقادیر خصوصی در localStorage یا sessionStorage ذخیره نمی‌شوند.

## ذخیره‌سازی و سازگاری

کلید و chain داخل `xrayconfig.Profile.TLS` خصوصی قرار می‌گیرند و مانند سایر
پروفایل‌ها با AEAD رمز می‌شوند. کانفیگ خصوصی Core از آرایه‌های inline PEM
استفاده می‌کند؛ هیچ مسیر فایل ارسالی مرورگر یا قابلیت نصب فایل روی نود اضافه
نشده است. پاسخ‌های عمومی فقط `NativeInbound.tls` حاوی metadata دارند.

| محل | فرمت جدید | دلیل |
| --- | --- | --- |
| پروفایل خصوصی TLS یا شبکهٔ جدید | `DXPPRF5\0` با AAD نسخهٔ ۵ | جلوگیری از بازنویسی داده‌ای که خوانندهٔ قدیمی نمی‌فهمد. |
| پلن عمومی و رسید TLS | `DXPPLN3\0` با AAD نسخهٔ ۳ | حفظ امنیت انتخاب‌شده و metadata در بازخوانی و تاریخچه. |
| پروفایل و پلن قدیمی REALITY | حداقل نسخهٔ سازگار قبلی | حفظ سازگاری و hashهای قدیمی. |

JSON احراز‌شده همچنان فیلد ناشناخته، کلید تکراری و دادهٔ اضافی را رد می‌کند.
APIهای عمومی قدیمیِ ساخت و ویرایش اینباند، TLS و شبکه‌های جدید را قبول نمی‌کنند؛
این امکانات متعلق به ویرایشگر کامل پلن هستند. حفاظت Store و SQLite در برابر
فعال‌سازی، تخصیص نود یا اتصال مشتری به پلن غیرفعال حفظ می‌شود.

قبل از بازگرداندن باینری قبلی، نویسنده باید متوقف و هر سه محل پروفایل، پلن و
رسیدهای تاریخی بررسی شوند. وجود v5 پروفایل یا v3 پلن/رسید، بازگشت به خوانندهٔ
قبلی را مسدود می‌کند. فقط خالی بودن پلن فعلی یا نبودن مشتری کافی نیست.

## آزمون و دامنهٔ باقی‌مانده

آزمون‌ها، اعتبارسنجی گواهی و کلید، محرمانگی پاسخ، نگهداری و تعویض کلید،
revision و replay، envelopeهای جدید و سازگاری داده‌های قدیمی را پوشش می‌دهند.
آزمون مرورگر واقعی با UI کامپایل‌شده، API احرازشده و SQLite موقت، ساخت TLS
با WebSocket، ویرایش به HTTP Upgrade بدون ارسال دوبارهٔ کلید، رد کلید نامنطبق
و تعویض موفق گواهی را اجرا می‌کند. داده‌های مشتری و کانفیگ اینباند نامرتبط
پیش و پس از این چرخه مقایسه می‌شوند.

آزمون Core از نسخه و checksum ثابت پروژه استفاده می‌کند و اتصال‌های خروجی
codec را با payload محدود روی loopback بررسی می‌کند. آزمون‌های منفی به
رفتار واقعی همان transport متکی‌اند؛ صرف عبور از `xray -test` اثبات انتقال
ترافیک یا اعتماد گواهی نیست. CI باید قبل از نصب LAB سبز باشد.

صدور یا تمدید خودکار ACME، early data و Headerهای سفارشی، TLS Fallback،
mKCP و سایر پروتکل‌ها در این قرارداد نیستند. مسیر عمومی **پلن → مشتری →
فعال‌سازی حسابداری‌شده → اثبات سلامت → اشتراک** همچنان مرحلهٔ اجرایی جدا دارد.
