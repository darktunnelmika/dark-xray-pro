# آماده‌سازی طرح ذخیره‌شده برای اجرای حسابداری‌شده

این مرحله، اتصال میان [ویرایشگر کامل اینباند](inbound-editor-unified-flow.fa.md)
و مسیر موجود Stage / Apply / Drain را برقرار می‌کند. ذخیرهٔ معمولی فرم همچنان
یک طرح متوقف‌شده می‌سازد. مالک با عملیات جداگانهٔ «آماده‌سازی اجرای LAB»، همان
طرح را همراه با کلاینت‌های انتخاب‌شده به تخصیص نود و پیش‌نویس اجرایی تبدیل می‌کند.
این عملیات به‌تنهایی هسته را اجرا نمی‌کند، پورت را باز نمی‌کند و اشتراک نمی‌سازد.

## محدودهٔ اجرایی این مرحله

| مورد | قرارداد |
| --- | --- |
| پروتکل و امنیت | VLESS / REALITY / TCP / Vision |
| مسیر | فقط Direct؛ کل طرح باید در همین محدوده باشد. |
| نود | دقیقاً یک نصب جفت‌شده، در فهرست صریح راه‌اندازی HUB، با کانال حسابداری مستقل و خالی |
| Listen IP | `127.0.0.1` در محیط ایزوله |
| پورت | پورت ثبت‌شدهٔ همان طرح؛ ۱۰۲۴ تا ۶۵۵۳۵، با حفظ رزروهای پروژه |
| Host | فهرست ذخیره‌شده به پیش‌نویس اجرایی منتقل می‌شود؛ مدرک دسترسی یا مجوز انتشار نیست. |
| کلاینت‌ها | انتخاب صریح ۱ تا ۵۰۰ مشتری موجود و واجد شرایط؛ سقف همان عملیات گروهی فعلی پروژه است. |
| تنظیمات پیشرفته | در این پذیرش اولیه، پروفایل دارای گزینهٔ پیشرفته یا override مربوط به endpoint آمادهٔ اجرا نمی‌شود. |

TLS، gRPC، XHTTP، WebSocket، HTTPUpgrade، Tunnel، Swap و گزینه‌های پیشرفته
همچنان در ویرایشگر قابل ذخیره‌اند. تلاش برای آماده‌سازی چنین طرحی، دلیل مشخص
می‌دهد و طرح را تغییر نمی‌دهد. هیچ بخشی از طرح حذف یا به حالت پیش‌فرض تبدیل
نمی‌شود تا به‌زور وارد محدودهٔ اجرایی شود.

این محدوده از قرارداد فعلی تسویهٔ نهایی TCP می‌آید. آزمون موفق handshake یا
رندر TLS به‌تنهایی، تسویهٔ مصرف هنگام قطع اتصال و restart را اثبات نمی‌کند.
دامنهٔ هستهٔ فعلی در [حسابداری فعال TCP](inbounds-p0h4-active-tcp-settlement.md)
و [مسیر HUB و Agent](inbounds-p0h6-metered-hub-agent.md) ثبت شده است.

## جریان مالک در پنل

چهار بخش Connection / Dark Swap / Advanced / Review تغییر نمی‌کنند؛ انتخاب
نود، پورت‌ها، Direct/Tunnel و Hostها همچنان در Dark Swap هستند.

در نمای خلاصهٔ طرح ذخیره‌شده، بخش آماده‌سازی این موارد را نشان می‌دهد:

1. قابلیت فعلی سرور، هویت نصب نود و موانع مربوط به همان طرح؛
2. جست‌وجو و انتخاب مشتریان موجود، همراه با دلیل عملیات؛
3. بازبینی نسخهٔ دقیق طرح و پروفایل، پورت، Hostها و مجموعهٔ مشتریان؛
4. تأیید صریح آماده‌سازی و رسید نتیجه.

پس از آماده‌سازی، وضعیت «آمادهٔ LAB» نمایش داده می‌شود. کنترل موجود اجرای نود
به همان نود، نصب و اینباند متصل می‌شود. Stage، Apply، Renew و Drain از قرارداد
قبلی استفاده می‌کنند؛ آماده‌سازی هیچ‌کدام را خودکار ارسال نمی‌کند.

گزارش اجرای موفق باید از وضعیت تازه و منطبق Agent و lease معتبر بیاید. رسید
ذخیره، وجود binding، ثبت یک فرمان یا حتی ACK تاریخی به‌تنهایی نشان‌دهندهٔ اتصال
فعال مشتری نیست. خروجی اشتراک نیز در این مرحله منتشر نمی‌شود.

## قرارداد API

همهٔ مسیرها فقط برای نشست مرورگر مالک هستند. POSTها به Origin و CSRF معتبر
نیاز دارند. bearer مالک، نماینده و صفحهٔ Agent مجوز این عملیات را نمی‌گیرند.

| روش و مسیر | نتیجه |
| --- | --- |
| `GET /api/v1/workspace/native-inbound-plans/{id}/promotion` | قابلیت، موانع خواندنی و رسید آماده‌سازی قبلی |
| `POST .../promotion/preview` | بازبینی بدون نوشتن، با نسخه‌های مورد انتظار و کلاینت‌های انتخاب‌شده |
| `POST .../promotion` | ثبت اتمیک با hash همان بازبینی و `confirmed:true` |

ورودی بازبینی شامل `event_id`، `expected_plan_revision`،
`expected_inbound_revision`، `client_ids` و `reason` است. ثبت نهایی
`review_sha256` و تأیید صریح را اضافه می‌کند. مسیر عددی غیرcanonical، query
اضافی، فیلد ناشناخته، فیلد تکراری و `null` پذیرفته نمی‌شوند.

hash بازبینی به شناسهٔ رویداد و دلیل عملیات، طرح، پروفایل، نسخه‌ها، مجموعهٔ دقیق مشتریان، تنظیمات تولیدشده،
نصب نود، pin هسته و نمونهٔ اجرای مشاهده‌شده متصل است. سرور هنگام ثبت، صلاحیت
مشتریان، quota، انقضا، وضعیت نماینده، رزرو پورت و تازه‌بودن مشاهدهٔ امضاشدهٔ
Agent را دوباره بررسی می‌کند. گزارش تازهٔ همان اجرای خالی، صرفاً به‌دلیل تغییر
زمان poll، بازبینی را باطل نمی‌کند؛ تغییر هویت اجرا یا اختیار ثبت‌شده آن را
نامعتبر می‌کند.

ثبت نخست HTTP 201 و تکرار دقیق همان رویداد HTTP 200 دارد. تکرار، همان رسید
تاریخی را برمی‌گرداند؛ کلید، UUID، revision، زمان ثبت یا binding تازه نمی‌سازد.
مرورگر درخواست نامطمئن را برای تکرار دقیق نگه می‌دارد و پس از reload نتیجهٔ
همان رویداد را با رسید سرور تطبیق می‌دهد.

POST تکراری نیز ابتدا مجوز فعلی startup و هویت جفت‌شدهٔ نود را بررسی می‌کند.
اگر پس از ثبت موفق، این مجوز خاموش یا هویت نصب عوض شده باشد، POST اجازهٔ
اجرا نمی‌گیرد؛ GET همچنان رسید تاریخی را کنار موانع فعلی برمی‌گرداند تا مرورگر
نتیجهٔ ثبت قبلی را بدون نوشتن دوباره تطبیق دهد.

## تراکنش و حفاظت داده

در یک تراکنش SQLite، رسید رمز‌شدهٔ آماده‌سازی، مجموعهٔ مشتریان انتخاب‌شده،
revision جدید پروفایل، تخصیص دقیق نود و پورت، bindingها و پیش‌نویس اجرایی ثبت
می‌شوند. قبل از commit، همان کامپایلر حسابداری که Stage استفاده می‌کند، نتیجه
را اعتبارسنجی می‌کند. خطا در آخرین نوشتن یا این بررسی، همهٔ تغییرات را برمی‌گرداند.

طرح اصلی و تمام رسیدهای ساخت و ویرایش آن حفظ می‌شوند. شناسهٔ اینباند، کلید
REALITY، UUID مشتری، اعتبار نماینده، دفتر مصرف و تاریخ مالی بازنویسی نمی‌شوند.
رسید عمومی آماده‌سازی فاقد کلید خصوصی، UUID مشتری و JSON خصوصی هسته است.

در این مرحله، طرح آماده‌شده و پیش‌نویس آن ثابت می‌مانند. مسیرهای عمومیِ ویرایش
پروفایل، تغییر target، اتصال/جداسازی مشتری و archive این طرح را تغییر نمی‌دهند.
این محدودیت در Store و triggerهای SQLite اعمال می‌شود تا خوانندهٔ قدیمی نیز
از مسیرهای عمومی آن را دور نزند. کنترل توقف اجرای این مسیر، Drain با تسویهٔ
حسابداری است. ویرایش و بازآماده‌سازی طرح اجرایی، قرارداد جداگانهٔ بعدی می‌خواهد.

## فعال‌سازی زیرساخت و بازگشت نسخه

قابلیت جدید به‌طور پیش‌فرض خاموش است. فعال‌سازی صریحِ
`DARK_PRO_ENABLE_INBOUND_PLAN_PROMOTION=1` به تنظیمات موجود LAB، دفتر مصرف،
Native Inbounds، ارتباط اختصاصی Agent TLS و
`DARK_PRO_ENABLE_METERED_ROUTE_TRANSACTIONS=1` وابسته است. فهرست startup باید
دقیقاً یک نود و نصب تأییدشده و pin هستهٔ مستقل را مشخص کند. مرورگر هیچ‌یک از
این تنظیمات را فعال یا ویرایش نمی‌کند.

این opt-in امکان رزرو یک کانال واقعاً خالی را می‌دهد. مسیر قدیمی Claim همچنان
شرط قبلی خود را دارد؛ کامپایل candidate و Stage/Apply نیز بدون target، binding
و پیش‌نویس معتبر اجرا نمی‌شوند. رزرو جدید اجازهٔ افزودن target عمومی به آن نود
را نمی‌دهد. پس از آماده‌سازی، شرط رسید اولیهٔ مصرف پیش از بازشدن پورت، همان
شرط موجود باقی می‌ماند.

جدول‌های افزوده، schema عادی ۸ را تغییر نمی‌دهند. با این حال وجود هر رکورد در
`native_inbound_plan_promotion_nodes`، `native_inbound_plan_promotions` یا
`native_inbound_plan_promotion_clients` یعنی
بازگشت به نویسنده‌ای که این قرارداد را نمی‌شناسد، مجاز نیست. پیش از هر rollback،
نویسنده باید متوقف و این رکوردها نیز کنار نسخه‌های فرمت پروفایل و رسید بررسی
شوند. حذف رسید یا بازگرداندن دیتابیس قدیمی برای ممکن‌کردن rollback مجاز نیست.

## شواهد پذیرش و ادامهٔ مسیر

- Store: اتمیک‌بودن، خطای دیرهنگام، CAS میان دو اتصال، hash بازبینی، تغییر صلاحیت
  مشتری، رمزنگاری رسید، تکرار دقیق، رزرو نود و جلوگیری از تغییر با SQL قدیمی.
- API: نشست مالک، CSRF، جداسازی Agent، opt-in صریح، JSON بدون ابهام، رسید
  عمومی و ورود طرح آماده‌شده به صف واقعی Stage.
- مرورگر: انتخاب مشتری، بازبینی، پاسخ نامطمئن و retry، reload، موانع دقیق،
  وضعیت آماده در برابر اجرا، کنترل نود مشخص و نمایش فارسی/انگلیسی در ۳۲۰px.
- مرورگر کامپایل‌شده با API و SQLite واقعی: آماده‌سازی همان طرح ذخیره‌شده و
  مقایسهٔ مشتریان، اعتبار، رویدادهای مالی و runtime نامرتبط قبل و بعد.
- Xray واقعی در namespace ایزوله: طرح ذخیره‌شده ← آماده‌سازی ← Stage/Apply ←
  رسید اولیه پیش از listener ← جریان واقعی مشتری ← Drain و رسید نهایی، همراه
  با ACK گم‌شده و بازگشایی بدون مصرف یا اجرای تکراری. این حالت در CI سه بار
  اجرا می‌شود و marker مستقل `PLAN_PROMOTION_ACTIVE_PASS` لازم دارد.

مسیر مستقل [سلامت اولین Apply و خروجی اشتراک LAB](inbound-initial-apply-health.fa.md)
اکنون این زنجیره را با آماده‌سازی حساب آزمون پیش از Stage، اثبات نسخهٔ ۴ و
خروجی متصل به همان round ادامه می‌دهد. مهلت محدود و opt-in جداگانهٔ آن حفظ
می‌شود؛ ساخت handover صوری یا استفاده از ACK به‌جای اثبات اتصال انجام نمی‌شود.
گسترش دامنهٔ اجرایی به TLS و شبکه‌های دیگر، Tunnel/Swap و ویرایش طرح آماده‌شده
نیز ادامهٔ همین مسیر است. انتقال دادهٔ HUB قدیمی و مشتریان عملیاتی جزو این
مرحله نیست.
