# API فروشگاه متصل (`/api/tenant/v1`)

[English](tenant-api.md) — مرجع کامل فیلدها و نمونه‌ها در نسخهٔ انگلیسی است.

**فروشگاه متصل** یک سیستم فروش بیرونی است (مثلاً سایتی با نماینده، کیف پول و ربات‌های خودش) که مشتری‌هایش را روی این پنل نگه می‌دارد. پنل منبع اصلی UUID، حجم، تاریخ و ساب هر مشتری است و سایت فقط می‌فروشد.

فروشگاه متصل نماینده نیست: اعتبار، برگشت پول، ربات تلگرام و فروشگاه داخل پنل ندارد و کاربرهایش هرگز با کاربرهای مالک یا نماینده‌ها قاطی نمی‌شوند:

- فقط کلید همان فروشگاه آن‌ها را می‌بیند و تغییر می‌دهد؛
- نماینده‌ها و زیرنماینده‌ها هرگز آن‌ها را نمی‌بینند؛
- مالک به‌صورت پیش‌فرض فقط خلاصه را می‌بیند (تعداد، فعال، آنلاین، حجم، مصرف). دیدن یا تغییر جزئیات به تنظیم «دسترسی مالک» (`read` یا `write`) نیاز دارد و هر بار در گزارش تغییرات ثبت می‌شود؛
- در لیست کاربرهای مالک، آمار فروش، یادآوری‌ها، ربات‌ها و فروشگاه پنل و webhook خود پنل نمی‌آیند و پنل هیچ پیامی به مشتری فروشگاه نمی‌فرستد.

## راه‌اندازی (مالک)

پنل ← **کاربران و نماینده‌ها ← فروشگاه‌های متصل ← افزودن**: شناسهٔ ثابت (مثلاً `tishtar`)، نام، سقف‌های اختیاری و اینباندهای مجاز. بعد **کلیدهای API ← کلید جدید**: کلید (`dt_<id>_<secret>`) فقط یک بار نشان داده می‌شود و فقط هش آن ذخیره می‌شود. کلید می‌تواند انقضا و لیست IP مجاز داشته باشد.

**برند و صفحهٔ اشتراک**: عنوان، آیدی تلگرام، اعلان، رنگ، لوگو، نام کانفیگ‌ها و دامنهٔ ساب خود فروشگاه. مشتری‌های فروشگاه هیچ چیزی از برند پنل نمی‌بینند.

## صدا زدن API

در هر درخواست: `Authorization: Bearer dt_…` (یا `X-API-Key`). خطاها به شکل `{"error": "...", "code": "invalid|not_found|conflict|policy|unauthorized|unavailable"}` برمی‌گردند. هر تغییر با نام `tenant:<id>` در گزارش تغییرات ثبت می‌شود.

| کار | مسیر |
|---|---|
| اطلاعات فروشگاه | `GET /me` |
| لیست کاربرها (صفحه‌به‌صفحه) | `GET /clients?after=&limit=` |
| جست‌وجو با شناسهٔ بیرونی | `GET /clients?external_ref=` |
| ساخت (با UUID، رمز Trojan، توکن ساب، external_ref، حجم، تاریخ، IP، دستگاه، اینباند — همه اختیاری) | `POST /clients` |
| خواندن / تغییر / حذف | `GET`، `PATCH`، `DELETE /clients/{name}` |
| فعال / غیرفعال | `POST /clients/{name}/enable`، `/disable` |
| ریست مصرف | `POST /clients/{name}/reset` |
| تمدید (افزودن حجم و روز) | `POST /clients/{name}/renew` |
| لینک ساب جدید یا کلیدهای جدید | `POST /clients/{name}/rotate` |
| لینک ساب و لینک‌های جدا | `GET /clients/{name}/links` |
| ساخت، تغییر، تمدید و حذف گروهی (تا ۵۰۰) | `POST /bulk/create`، `/bulk/update`، `/bulk/renew`، `/bulk/delete` |
| همهٔ تغییرات مصرف و وضعیت از cursor قبلی | `GET /changes?cursor=` |
| webhook خود فروشگاه | `GET`/`PUT /webhook`، `POST /webhook/test` |
| کانفیگ‌ها و مصرف تا ۵۰۰ کاربر با هم | `POST /bulk/links` با `{"names": [...]}` |
| افزودن مصرفِ پنل قبلی به تا ۵۰۰ کاربر | `POST /bulk/add-usage` با `{"clients": [{"name", "add_bytes"}]}` |

**مصرف قبلی:** `used_bytes` فقط موقع ساخت کاربر داده می‌شود: مصرفی که کاربر در پنل قبلی داشته. از حجم کاربر کم می‌شود. تا وقتی اپ مشتری‌ها هنوز به سرورهای قدیمی وصل می‌شوند، مصرفی که آن سرورها گزارش می‌دهند را با `/bulk/add-usage` اضافه کنید. با این کار `rev` کاربر جلو می‌رود و در فید تغییرات دیده می‌شود. این مصرف در جمع کل و userinfo ساب حساب می‌شود، ولی در تاریخچه‌ی روزانه و تفکیک نود نمی‌آید.
| چه کسی از چه زمانی ساب را آپدیت کرده | `GET /sub-fetches?since=&list=not_fetched` |

**نسخهٔ کانفیگ‌ها (`links_version`):** هر جواب `/changes` و `/bulk/links` یک `links_version` دارد. این یک hash از چیزهایی است که کانفیگ‌ها جدا از خود کاربر از آن ساخته می‌شوند: اینباندها، hostها، مسیرها، برند و مسیریابی. وقتی مالک یک host یا مسیر را عوض کند، این عدد (حداکثر تا ۱۵ ثانیه بعد) عوض می‌شود. سایتی که کانفیگ‌ها را نگه می‌دارد (مثلاً پل ساب) در این حالت همه را دوباره با `/bulk/links` می‌خواند. تغییر یک کاربر فقط `rev` همان کاربر را جلو می‌برد.

در `/bulk/links` برای هر کاربر این‌ها برمی‌گردد: `links` (همان چیزی که ساب الان دارد؛ برای کاربر خاموش یا منقضی خالی است)، `userinfo` (مقدار هدر `Subscription-Userinfo`)، مصرف، حجم، انقضا و `sub_fetched_unix`. نام ناشناس با `"error": "not_found"` برمی‌گردد و کل درخواست را خراب نمی‌کند. خواندن کانفیگ‌ها در گزارش تغییرات ثبت نمی‌شود.

`sub_fetched_unix` در شیء کاربر آخرین زمانی است که اپ کاربر ساب را از این پنل گرفته (۰ یعنی هنوز نگرفته). هر ۳۰ ثانیه ثبت می‌شود.

## webhook

فقط رویدادهای کاربرهای همان فروشگاه فرستاده می‌شود: `blocked:expired|volume|ips`، `reset:*`، `next-plan` و `device-refused`؛ دسته‌های ۵۰تایی، با امضای HMAC-SHA256 در `X-Dark-Signature`. cursor فقط بعد از جواب 2xx جلو می‌رود. نمونهٔ بررسی امضا در PHP در نسخهٔ انگلیسی هست.

## انتقال مشتری‌ها

- از 3x-ui، مرزبان یا پاسارگارد: **تنظیمات ← پشتیبان و انتقال ← ورود از پنل دیگر**، مقصد «فروشگاه متصل». UUID، رمز Trojan، subId، حجم، تاریخ و مصرف حفظ می‌شود و لینک‌های ساب قدیمی جواب می‌دهند. اول پیش‌نمایش بگیرید.
- بین مالک، نماینده‌ها و فروشگاه‌ها: **فروشگاه‌های متصل ← جابه‌جایی کاربرها** (با پیش‌نمایش؛ لیست خالی یعنی همهٔ کاربرهای مبدأ).

## دامنهٔ ساب قدیمی

با این بخش، لینک قدیمی مشتری‌ها بدون تغییر کار می‌کند: کافی است دامنهٔ ساب قدیمی به هاب اشاره کند. تنظیمش در **فروشگاه‌های متصل ← دامنه‌های ساب** است (مالک)، یا با `PUT /api/v2/admin/tenants/{id}/sub-domains/{domain}`:

```json
{"port": 2096, "tls": true, "prefix": "/2fmgkwhmfhyat8zr/", "fallback": "https://203.0.113.5:2096", "enabled": true}
```

- **پورت:** دامنه روی همان پورت جواب می‌دهد. چند دامنه می‌توانند یک پورت مشترک داشته باشند؛ گواهی بر اساس SNI و دامنه بر اساس `Host` انتخاب می‌شود.
- **پیشوند مسیر:** `prefix` مسیر قدیمی قبل از subId است. اگر خالی باشد، هر مسیری که به subId ختم شود قبول می‌شود.
- **فقط کاربرهای همین فروشگاه** جواب می‌گیرند، با همان ساب و همان هدرهای `/sub/<id>`.
- **subId ناشناس** به `fallback` (پنل قدیمی) داده می‌شود:
  - هاب با IP پنل قدیمی وصل می‌شود ولی با نام دامنه درخواست می‌دهد، پس گواهی پنل قدیمی بررسی می‌شود.
  - فقط جواب ۲۰۰ِ غیرخالی رد می‌شود؛ هر جواب دیگری 404 می‌شود. **هیچ‌وقت لیست خالی برنمی‌گردد**، چون بعضی اپ‌ها با لیست خالی همهٔ کانفیگ‌ها را پاک می‌کنند.
  - اگر fallback تنظیم نشده باشد، subId ناشناس 404 می‌گیرد.
- **گواهی:** رکورد A دامنه را روی IP هاب بگذارید و «بررسی DNS و گواهی» را بزنید. گواهی با ACME و HTTP-01 روی هاب گرفته می‌شود. اگر نشد، هر ۱۰ دقیقه دوباره تلاش می‌شود.
- **کش:** ساب هر کاربر فروشگاه ۳۰ ثانیه نگه داشته می‌شود، تا وقتی هزاران اپ با هم آپدیت می‌کنند فقط یک بار ساخته شود.
- **گزارش آپدیت:** همین پنجره نشان می‌دهد چند نفر ساب را آپدیت کرده‌اند و چند نفر نه. نسخهٔ API آن `GET /api/v2/admin/tenants/{id}/sub-fetches` است.
