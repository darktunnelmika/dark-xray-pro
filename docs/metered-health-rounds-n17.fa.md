# N17 — دورهٔ کامل و تکرارپذیر آزمون سلامت مقصد

این مرحله پوشش سلامت پروتکل را از یک درخواست برای یک اینباند، به یک دورهٔ ثبت‌شده برای **تمام اینباندهای تنظیمات اجراشدهٔ مقصد** تبدیل می‌کند. نتیجه هنوز فقط شاهد محدود سلامت مسیر پروتکل در LAB است؛ `can_publish` همواره `false` می‌ماند. این تغییر هیچ استقرار، فعال‌سازی Xray، انتقال واقعی یا تغییری در HUB قدیمی انجام نمی‌دهد.

## مجموعهٔ کامل و مهلت ثابت

HUB مجموعهٔ لازم را از ارجاع‌های دقیق پیش‌نویسِ فرمان Apply و listenerهای همان candidate اجراشده استخراج می‌کند. این دو مجموعه باید دقیقاً متناظر باشند؛ اینباند یا پورت تکراری، عضو جاافتاده، هویت آزمون مفقود و هر مسیر پشتیبانی‌نشده، کل درخواست را رد می‌کند. سقف هر دوره **۲۵۶ اینباند یکتا** است. ورودی مرورگر هیچ فهرست عضو، پورت، URL یا مهلتی ندارد.

اعضا، bindingها و hash مجموعه در یک تراکنش ثبت می‌شوند. هر عضو intent و challenge مستقل دارد؛ رسید یک اینباند نمی‌تواند عضو دیگری یا دورهٔ بعدی را پوشش دهد. مهلت تمام اعضا، مهلت اصلی همان دوره است: حداکثر **۸ ثانیه از ایجاد** و هرگز بعد از پایان lease مقصد. این سقف تضمین نمی‌کند که آزمون ۲۵۶ عضو در آن زمان تمام شود؛ پوشش ناقص یا دیررس معتبر نمی‌شود.

تنها یک دورهٔ منقضی‌نشده برای هر handover مجاز است. دورهٔ تازه پس از انقضای قبلی، ID تازه و اثبات‌های تازه می‌خواهد. retry همان ID، همان مجموعه و مهلت اصلی را برمی‌گرداند و آزمون یا lease را تمدید نمی‌کند. ثبت رسید و مسیرهای retry، نسل تنظیمات، مصرف مشتری، تسویه یا رزرو نودها را تغییر نمی‌دهند.

منبع پیاده‌سازی: [round و manifest](../internal/business/metered_health_rounds.go)، [binding و پذیرش اثبات](../internal/business/metered_health.go)، [صف و poll](../internal/business/metered_health_queue.go).

## معنی وضعیت‌ها

وضعیت هنگام خواندن audit از دادهٔ پایدار و وضعیت جاری استخراج می‌شود؛ یک پرچم پایدار برای آماده‌بودن عمومی یا اجازهٔ انتشار نیست.

| وضعیت | معنی |
| --- | --- |
| `pending` | binding جاری معتبر است، اما حداقل یک عضو رسید پذیرفته‌شده ندارد. |
| `complete` | همهٔ اعضا رسید دارند و بررسی دقیق وضعیت جاری موفق است. فقط در همین حالت و پیش از انقضا، `current=true` می‌شود. |
| `expired` | مهلت اصلی تمام شده است؛ حتی مجموعهٔ کامل رسیدهای تاریخی، سلامت فعلی را تأیید نمی‌کند. |
| `state_changed` | مبدأ، مقصد، Apply، configuration، epoch، مشاهده یا lease دیگر با binding دوره سازگار نیست. |

بازخوانی رسید پذیرفته‌شده، شاهد تاریخی را حفظ می‌کند؛ به درخواست قدیمی اختیار اجرای دوباره نمی‌دهد. audit حداکثر ۵۰ دورهٔ اخیر را با metadata امن و بدون credential، تنظیمات خصوصی یا بستهٔ امضاشدهٔ Agent برمی‌گرداند. `health_rounds` در audit بدون دوره نیز آرایهٔ خالی است.

منبع: [audit](../internal/business/metered_handover_audit.go) و [آزمون‌های تکرار، هم‌زمانی و پوشش کامل](../internal/business/metered_health_rounds_test.go).

## API مالک و رابط کاربری

مسیر جدید فقط برای نشست مرورگری مالک، با CSRF و Origin معتبر و همان allowlist نصبِ هر دو نود در دسترس است:

```http
POST /api/v1/workspace/metered-handovers/{handover_id}/health-rounds
Content-Type: application/json

{"id":"0123456789abcdef0123456789abcdef","confirmed":true}
```

`id` دقیقاً ۳۲ رقم hex کوچک است. فیلدهای اضافی، انتخاب زیرمجموعهٔ اینباندها و انتخاب verifier رد می‌شوند. پاسخ موفق `202` است. flag جدید `DARK_PRO_ENABLE_METERED_HEALTH_ROUNDS=1` فقط هنگام راه‌اندازی خوانده می‌شود و به فعال‌بودن صریح `DARK_PRO_ENABLE_METERED_HEALTH=1` و transport سلامت با verifier ازپیش‌پین‌شده نیاز دارد. هیچ مسیر مرورگری این قابلیت را فعال یا پایگاه را مهاجرت نمی‌دهد.

Discovery مقدار `health_rounds_enabled` را اعلام می‌کند. با فعال‌بودن آن، UI به‌جای انتخاب یک اینباند، اقدام «آزمون همهٔ اینباندهای مقصد» و تعداد رسیدهای پذیرفته‌شده را نشان می‌دهد. درخواست فقط پس از تأیید جداگانه ارسال می‌شود. در قطع پاسخ، همان body و ID در `sessionStorage` حفظ می‌شوند؛ reload یا refresh درخواست تازه‌ای نمی‌سازد و retry همچنان کلیک و تأیید می‌خواهد. پاسخ ثبت‌شده با audit تطبیق داده می‌شود. رابط قدیمی N15 برای قابلیت قدیمی حفظ شده است.

UI رسید تاریخی را از سلامت جاری جدا می‌کند. ادعای جاری به پوشش تمام اینباندهای مقصد، مشاهدهٔ تازه، lease معتبر و مهلت دوره وابسته است؛ پس از انقضا، خطای خواندن یا تغییر وضعیت نمایش داده نمی‌شود. `can_publish=true`، عضو تکراری، نصب نامنطبق و ادعای جاری برای پوشش ناقص، پذیرفته نمی‌شوند. متن و جریان فارسی در عرض ۳۲۰ پیکسل نیز آزموده شده‌اند.

منبع: [API](../internal/api/metered_health.go)، [startup](../cmd/hub/main.go)، [UI](../web/src/MeteredHandovers.tsx)، [اعتبارسنجی پاسخ و retry](../web/src/meteredHandovers.ts). allowlist محدود nginx اکنون هر دو مسیر `/health` و `/health-rounds` را فقط با `POST` عبور می‌دهد: [پیکربندی](../ops/nginx/node-manager.conf)، [ماتریس آزمون](../scripts/test-node-manager-proxy.py).

## ذخیره‌سازی، Agent و محدودیت بازگشت

Schema پیش‌فرض پایگاه تازه همچنان **v8** است. فعال‌سازی صریح دورهای سلامت، schema افزایشی **v12** را پس از قابلیت‌های لازم ایجاد می‌کند؛ رسیدهای legacy حذف یا به اثبات کامل تبدیل نمی‌شوند. خاموش‌کردن flag نسخهٔ پایگاه را پایین نمی‌آورد. HUB قدیمی که v12 را نمی‌شناسد، آن را رد می‌کند؛ دست‌کاری `user_version` یا حذف جدول‌ها راه بازگشت سازگار نیست. بازگشت باینری باید با وضعیت و نسخهٔ پشتیبان سازگار و بررسی‌شده انجام شود. [schema و آزمون سازگاری](../internal/usageledger/health_rounds_schema.go)

ژورنال durableِ Agent به **v3** ارتقا یافته، اما نسخهٔ فرمان‌ها و wire metered همچنان **v2** است. Agent جدید ژورنال مجاز قبلی را می‌خواند؛ Agent قدیمی ژورنال v3 را رد می‌کند. attempt پیش از I/O و رسید دقیق پیش از ارسال به HUB ذخیره می‌شوند. crash در فاصلهٔ این دو ذخیره، وضعیت نامعلوم ایجاد می‌کند و مجوز اجرای دوبارهٔ همان nonce نیست.

ژورنال حداکثر **۵۱۲ attempt** نگه می‌دارد؛ رسید موفقی که هنوز ACK ندارد، حتی پس از انقضا تا پذیرش یا رد صریح HUB حفظ می‌شود. ظرفیت کامل باعث رد کار تازه می‌شود و attempt زنده برای بازکردن جا حذف نمی‌شود. حذف سوابق واجد شرایط همراه با barrier پایدار است تا عقب‌رفتن ساعت، درخواست حذف‌شده را دوباره قابل اجرا نکند. هر نوبت worker حداکثر **۵۱۲ گام کاری و ۱۲ ثانیه** دارد؛ پس از پذیرفته‌شدن یک عضو، عضو بعدی را بدون تحمیل فاصلهٔ idle poll پردازش می‌کند. این بودجه مهلت ۸ ثانیه‌ای دوره را تمدید نمی‌کند.

منبع: [ژورنال v3](../internal/managedxray/transaction_journal_linux.go)، [worker و outbox](../internal/managedxray/protocol_health_transport_linux.go)، [فراخوانی Agent](../cmd/node-agent/main.go).

## دامنهٔ اثبات و وضعیت آزمون‌ها

دامنهٔ فعلی فقط **Direct روی `127.0.0.1` با VLESS Reality / TCP / Vision** است. اعتبارسنجی خالص candidate پیش از ثبت دوره، کل مجموعه را در صورت وجود مسیر پشتیبانی‌نشده رد می‌کند. این آزمون، host یا port عمومی، مسیر دسترسی کاربر، DirectHost، CDN یا مصرف‌کنندهٔ subscription را اثبات نمی‌کند. [اعتبارسنجی پشتیبانی و probe](../internal/managedxray/protocol_health_linux.go)

در زمان ثبت این سند، نتایج محلی تأییدشده عبارت‌اند از:

- ساخت production وب با TypeScript و Vite موفق بود.
- هر **۱۵ آزمون مرورگری handover** موفق بود: ۶ مورد N17 برای پوشش دو اینباند، انقضای خودکار، پاسخ گمشده و retry یکسان پس از reload، رد دادهٔ ناسازگار و پوشش زیرمجموعه، حذف ادعای جاری پس از خطای خواندن یا تغییر وضعیت، و فارسی در عرض ۳۲۰ پیکسل؛ به‌همراه آزمون‌های قبلی N10/N15.
- اجرای `go test ./internal/api -run 'TestMeteredHealth|TestMeteredHandoverOwnerAPI|TestMeteredHandoverAPI' -count=1` موفق بود؛ شامل opt-in جداگانه، audit خالی پیش از اولین دوره، RBAC/CSRF/Origin، روش HTTP، ورودی محدود، replay دقیق و allowlist نصب هر دو نود.
- آزمون‌های محلی مجموعهٔ کامل در لایهٔ business موفق بودند. شواهد آن‌ها امضاشده و مصنوعی‌اند و جای آزمون شبکهٔ واقعی را نمی‌گیرند.
- بررسی syntax اسکریپت proxy موفق بود. اجرای ماتریس با nginx واقعی در محیط محلی انجام نشد، چون باینری nginx موجود نبود.

آزمون CI با هستهٔ Xray پین‌شده در namespace شبکهٔ جدا و کاربر غیرroot، برای سنجش دور چنداینباندیِ واقعی و مسیر owner→Agent→receipt لازم است. **این سند هنوز موفقیت حالت جدید real-core را ادعا نمی‌کند**؛ نتیجهٔ آن باید در شواهد PR ثبت شود. ## مرحلهٔ بعد برای انتشار واقعی

این تغییر publisher نمی‌سازد. هنوز قرارداد کامل native برای ارائهٔ subscription، token مصرف‌کننده و read-store فعال وجود ندارد. مرحلهٔ انتشار باید این بخش‌ها را به‌هم متصل کند:

1. host، port و مسیر عمومیِ تأییدشده برای هر اینباند، همراه با آزمون انتهابه‌انتهای همان مسیری که کاربر واقعاً مصرف می‌کند.
2. endpoint ارائهٔ subscription، قرارداد token و دسترسی، و snapshot مشخصی از خروجی واقعی مصرف‌کننده.
3. تعویض اتمی pointer نسخهٔ فعال به همان snapshot، مشروط به اثبات کامل و جاری، Apply و binding دقیق؛ failure و retry نباید خروجی نیمه‌منتشر یا دو مقصد فعال بسازند.
4. قرارداد جداگانهٔ ادامهٔ lease پس از انتشار، ابطال سلامت، بازیابی و rollback. lease کوتاه و بدون تمدید خودکارِ امروز، به‌تنهایی چرخهٔ عمر یک اشتراک منتشرشده را تأمین نمی‌کند.

این مسیر نباید با تغییر دلخواه accounting، تسویه، generation یا آزادکردن زودهنگام رزرو نودها پیاده شود. تا تکمیل و آزمون مصرف‌کنندهٔ واقعی و چرخهٔ عمر آن، نتیجهٔ این مرحله همان «سلامت محدود تمام اینباندهای مقصد» است و مجوز انتشار محسوب نمی‌شود.
